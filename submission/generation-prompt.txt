# Mock service with Cloudflare Workers

Your flow's tools call a mock service that you write, instead of the real bank service. You publish this service as a free Cloudflare Worker. The `example/` folder here only shows the pattern: a Worker with a single endpoint (`POST /ping`). You will write the statement-debt services yourself.

## Requirements

- Node.js 18 or later
- A free Cloudflare account (dash.cloudflare.com)
- Wrangler (Cloudflare's command-line tool): runs without installing, via `npx wrangler ...`

## 1. Run the example locally

```bash
cd example
npx wrangler dev
```

The Worker opens at `http://localhost:8787`. Try it from another terminal:

```bash
curl -s -X POST http://localhost:8787/ping \
  -H 'content-type: application/json' \
  -d '{"kod": "A1"}'
```

The response is the same as `example/example-response.json`. For a code that does not exist it returns `404` and `{"hata": "kayıt bulunamadı"}`.

## 2. Publish it

```bash
npx wrangler login      # grant access to your Cloudflare account in the browser
npx wrangler deploy
```

The output shows the Worker address: `https://example-mock.<your-subdomain>.workers.dev`. To change the name, change the `name` field in `wrangler.toml`. Run `npx wrangler deploy` again whenever the code changes; the address stays the same.

Check after publishing:

```bash
curl -s https://example-mock.<your-subdomain>.workers.dev/health
```

## 3. Connect the tool in the Freya flow to the Worker

1. Add an API tool to the flow.
2. Enter the method and address: `POST https://<your-worker-name>.<your-subdomain>.workers.dev/<path>`. For the statement services, use the same path as under the bank's base address in `../sources/documents/2026-10-01-service-contract.md` (for example `/voice/v1/cards.list`).
3. In the request body, write variables in the form `{{variable_name}}`. Example: `{"data": {"customerNo": "{{customerNumber}}", "aiFlow": "..."}, "call": {...}}`. During the call, the variable's value is substituted in.
4. Take the fields you will use in the flow from the response into variables.

The "Test API Request" button in the panel may send the text `{{customerNumber}}` as is, without filling in the variables. In this case the example Worker returns a valid record instead of an error (`isTemplateVariable`). Doing the same in your own services makes testing easier.

## When writing your own services

- Endpoints, request and response fields must match `../sources/documents/2026-10-01-service-contract.md` exactly: the same path, the same field names (`data`/`call` request body, `data`/`result` response), the same date and amount format. The test customers' responses are in `../test-environment/test-customers.json`, explained in `../test-environment/test-customers.md`.
- Keep customer and card data in a table inside the Worker file (like `RECORDS` in the example). No database is needed.
- For a customer or card that is not found, return the error response from the contract; do not return made-up data.
- Responses should return data only (amount, date, status). The flow builds the sentence to be said to the customer.
- Do not put secret keys or real personal data in it; the Worker address is public.

# Credit cards: statements and payments

Answers to the questions we hear most often about your Yıldız credit card statement and how to pay it. Can't find what you need? Scroll to the bottom for ways to reach us.

---

**When will I get my statement?**

Once a month, on your statement date. Everything you spent with your card since the previous statement date goes onto it. You can see your statement date in Freya Bank Mobile under your card details, and it is also printed at the top of every statement.

**Can I change my statement date?**

Yes. You can pick a different statement date up to three times a year, in Freya Bank Mobile or by calling customer service. The new date applies from your next statement onwards. Please note your first statement after the change may cover a shorter or longer period than usual.

**How do I get my statement by e-mail?**

Just tell us where you'd like it sent. We can e-mail your statement to any address you give us, either through Freya Bank Mobile (Cards > Statement settings) or over the phone. E-mailed statements come as a PDF.

**I didn't receive my statement. What should I do?**

First check your spam or junk folder. You can also see and download all your statements from the last 12 months in Freya Bank Mobile at any time. If it's still missing, contact customer service and we'll send it again.

**What is the minimum payment?**

It is the smallest amount you need to pay by the due date to keep your card in good standing. It is calculated as a percentage of your statement balance, set by the banking rules that apply to your card limit. The exact amount is shown on your statement and in the app.

**What happens if I only pay the minimum?**

Your card stays in good standing, but interest is charged on the part of the balance you didn't pay. Paying the full statement balance is the only way to avoid interest.

**And if I pay less than the minimum, or nothing?**

Late payment interest is charged and it may affect your credit record. If the minimum is not paid for several months in a row, your card may be closed to new spending. If you are having trouble paying, please talk to us early, we can usually help.

**When is my payment due?**

Your due date is shown on your statement, usually about 10 days after the statement date. If the due date falls on a weekend or public holiday, it moves to the next working day.

**I spent in dollars, euros or pounds. How is that shown?**

Spending in a foreign currency is shown on your statement in that currency, separately from your Turkish lira spending. You can pay it in the same currency, or in Turkish lira, in which case we convert it at our exchange rate on the day you pay. Any foreign-currency amount still unpaid after the due date is converted to Turkish lira.

**How can I pay my card?**

- In Freya Bank Mobile: Cards > select your card > Pay. You can pay from any of your Freya Bank accounts.
- At any Freya Bank branch, in cash or from your account.
- At Freya Bank ATMs, with or without a card.
- Automatically: set up automatic payment and we'll take the minimum or the full amount from your account on the due date.

Payments in the app or at an ATM show on your card straight away. (Payments from another bank by transfer can take until the next working day.)

**Can I pay my card over the phone?**

You can check your balance and statement details on the phone line. For payments we recommend Freya Bank Mobile, it's the quickest way.

**Can I split my statement into instalments?**

For some purchases, yes, depending on the merchant and your card. Eligible transactions show an "Instalment" option in Freya Bank Mobile. Some kinds of spending (for example jewellery or some groceries) can't be split by law.

**There's a transaction on my statement I don't recognise. What do I do?**

Please contact customer service as soon as possible, by phone or through the "Messages" section in Freya Bank Mobile. Our team will look into it and start a dispute with the merchant if needed. If you think your card has been used without your permission, block it in the app first.

**Is my statement the same for all my cards?**

If you have more than one Yıldız card, each card gets its own statement, unless you have asked for a joint statement. Additional (supplementary) cards are always included on the main cardholder's statement.

# Voice assistant: statement and debt services, service contract

Author: Mert Koç, Integration Architecture, Freya Bank (mert.koc@freyabank.example)
Date: 1 October 2026
Distribution: Selin Aydın, Kerem Yalçın, Burcu Tan (Freya Bank); Deniz Arı (Freya)

> Mert: This is the contract the voice assistant integrates against for the statement / debt use case. It covers only the seven services the assistant calls. Everything about how the call reaches the assistant and how it goes back to the phone menu is Burcu's side and is not in here. If something below disagrees with what you see in the test environment, tell me and I'll check which side is wrong.

## 1. Before you start

- The caller is already identified when the assistant picks up. The phone menu hands over the **customer number** with the call, so there is no customer search service in this contract. Start from `cards.list`.
- Every service is `POST`, JSON in, JSON out, UTF-8.
- Base address for all seven:

```
https://api.freyabank.example/voice/v1/
```

  So the card list is `POST https://api.freyabank.example/voice/v1/cards.list`, and so on.
- Dates are strings in `dd.MM.yyyy` (e.g. `"05.11.2026"`). Amounts are JSON numbers with a dot as decimal separator (`5000.13`), never formatted strings. Do not round them.
- Turning numbers and dates into speech is the assistant's job. The services return raw values only, no sentences meant to be read to the caller (the `messageText` in errors is for logs, please don't read it out).

## 2. Access token

The services sit behind our API gateway. You need a bearer token first.

```
POST https://api.freyabank.example/oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&client_id=<client id>&client_secret=<client secret>&scope=voice.statement
```

Answer:

```json
{
  "access_token": "<token>",
  "token_type": "Bearer",
  "expires_in": 1800
}
```

Then on every service call:

| Header | Value |
|---|---|
| `Authorization` | `Bearer <token>` |
| `Content-Type` | `application/json` |
| `Accept` | `application/json` |

The token belongs to the integration (service account), not to the caller. Cache it and get a fresh one when it runs out; don't fetch one per call. Client id and secret: I'll send them over the secure channel, not by e-mail.

(Test environment: the token and headers are not checked there. Send them anyway so nothing changes when we switch.)

## 3. Envelope

### Request

```json
{
  "data": { "...service fields..." },
  "call": { "ani": "<caller's number>", "lang": "tr" }
}
```

`data` carries the fields of each service (section 5). `call` is call metadata we log on our side; nothing in this contract depends on it and the test environment ignores it.

### Response

Every answer has a `result` object. Successful answers also have `data`.

```json
{
  "data": { "...service fields..." },
  "result": {
    "guid": "f0e1d2c3b4a5968778695a4b3c2d0002",
    "returnCode": "1",
    "messageText": "Success",
    "code": "1",
    "message": "Success",
    "type": null,
    "details": {
      "guid": "f0e1d2c3b4a5968778695a4b3c2d0002",
      "rootCause": null,
      "errorOrigin": null
    }
  }
}
```

Success = HTTP 200 and `result.returnCode` is `"1"`. Anything else is an error, see section 4. `guid` is our trace id; if you open a ticket with us, give us the `guid`.

## 4. Errors

Error answers have **no `data` object**, only `result`:

```json
{
  "result": {
    "guid": "f0e1d2c3b4a5968778695a4b3c2d0086",
    "returnCode": "FBE00099",
    "messageText": "Teknik hata: ABORTED: ",
    "code": "FBE00099",
    "message": "Teknik hata: ABORTED: ",
    "type": "ERROR",
    "details": {
      "guid": "f0e1d2c3b4a5968778695a4b3c2d0086",
      "rootCause": "TechnicalError",
      "errorOrigin": "ivr-gateway-test:ivr-channel-v0"
    }
  }
}
```

`returnCode` and `code` always carry the same value, and so do `messageText` and `message`. `type` is `"ERROR"` or `"WARNING"`. `rootCause` and `errorOrigin` are diagnostic strings; log them, don't branch on them.

Codes you can get:

| HTTP | `code` | `type` | When | Services |
|---|---|---|---|---|
| 400 | `INVALID_ARGUMENTS_ERROR` | `ERROR` | A required field is missing or empty (message names the field, e.g. `"card number cannot be empty"`) | all |
| 401 | (gateway) | | Token missing or expired. Get a new token and retry once | all |
| 404 | `FB_IVR_CHANNEL_102` | `WARNING` | Customer has no valid card (message: `"Müşteriye ait geçerli kart bilgisi bulunamadı."`) | `cards.list` |
| 404 | `FB_IVR_CHANNEL_120` | `WARNING` | Card not found | `cards.balance` |
| 404 | `FB_IVR_CHANNEL_121` | `WARNING` | Card not found | `statement.week.get` |
| 404 | `FB_IVR_CHANNEL_107` | `WARNING` | No statement document to send (message: `"Pdf dokümanı bulunamadı"`) | `statement.pdf.send` |
| 500 | `FBE00099` | `ERROR` | Technical error on our side (message: `"Teknik hata: ABORTED: "`) | all |

Note on the `cards.list` 404: it's a WARNING, it means "this customer has no card the assistant can work with", not that the service is broken. How the assistant reacts to that vs. a 500 is for Selin's analysis, I'm only flagging that they are different things.

Timeouts: we haven't agreed a client timeout yet. Most answers are well under a second, but under load (and once in the test data) an answer can take longer than ten seconds and still succeed. Open point, see section 7.

## 5. Services

| # | Service | Called with | Gives back |
|---|---|---|---|
| 5.1 | `cards.list` | customer number | the customer's cards the assistant may talk about |
| 5.2 | `cards.balance` | card number | statement and due dates, debt per currency |
| 5.3 | `statement.week.get` | card number | the card's current statement week and day, joint statement info |
| 5.4 | `statement.week.decide` | card number + requested week | what the dates *would* be with that week (does not change anything) |
| 5.5 | `statement.week.change` | card number + requested week | changes the statement week |
| 5.6 | `contact.email.get` | customer number | registered e-mail / phone |
| 5.7 | `statement.pdf.send` | customer, card, currency, statement date, address | sends the statement PDF by e-mail |

Card number: always send the `cardNumber` **exactly as `cards.list` returned it**. Don't rebuild it from digits the caller says.

- Only the `data` fields decide the answer in test. Token, headers and `call` are not checked.

# Statement debt: self-service step for the voice assistant

Business analysis, working draft
Author: Selin Aydın (Card Self-Service, Freya Bank)
Date: 2 September 2026
Shared with: Kerem Yalçın, Burcu Tan, Mert Koç (for the service part)

> Kerem, Burcu: this is my first pass after the two walkthroughs of the phone menu. Comments inline please, I'll collect them before we sit down with the Freya team. Anything marked **TBD** I could not close myself.

---

## 0. In one paragraph

Today the menu plays a fixed announcement and that's it. With the assistant we want a short conversation instead: which card, how much is owed and by when, and then two things the caller can get done without waiting for an agent (statement PDF by mail, a different statement week). Paying stays with the agents for now. Whatever else the caller brings up, we hand back to the main menu.

## 1. Scope

In:
- Debt reading for one card at a time, all four currencies we carry (Lira, Dollar, Euro, Sterling), with the due date. When the closed statement is fully paid, the "no debt" wording plus the running total.
- The two follow-ups: mailing the statement (only ever to the address we hold) and moving the statement week.
- Choosing the card, where needed.

Out (first list, Kerem please extend):
- Paying the debt itself: handed to an agent.
- Disputes, "I paid but it doesn't show" (agent, see §7).
- Limits, cash advance, card blocking, anything about debit cards.
- Changing the e-mail address.
- Statements of earlier periods.

Burcu thinks statement debt is one of the top three menu choices; she'll try to get a figure.

## 2. How the caller arrives

The phone menu has already identified and authenticated the caller before the hand-over. The assistant receives the customer number with the call and does not run any identity check of its own.

**TBD:** the flow drawing we got from the vendor side has a box "second factor may be needed". I don't see why for a read-only step plus two low-risk actions; to confirm with Elçin.

## 3. Picking the card

The card list comes from `cards.list` (customer number in, eligible credit cards out). Then:

| Situation | What the assistant does |
|---|---|
| Caller already named the card when arriving | If the name fits exactly one card, no selection question. |
| Several cards | Asks which one, with at most two example names taken from the caller's own cards: “Hangi kartınızın borcunu öğrenmek istersiniz? Örneğin, Yıldız Premium veya Yıldız Pratik diyebilirsiniz.” |
| Caller asks for "all my cards" | Not possible, the debt service takes one card at a time. Selection question again (counts as a failed attempt). |
| Name not on the list | Tells the caller there is no card with that name and reads the eligible ones again. |
| Two or more cards with the same name | Asks for the last four digits: “Yıldız isimli birden fazla kartınız var. Kartınızın son dört hanesini söyler misiniz?” (name of the card in place of "Yıldız") |
| Same name and same last four | Asks for the full card number: “Son dört hanesi aynı olan birden fazla kartınız var. Kart numaranızın tamamını söyler misiniz?” |

Two easy cases outside the table: a single card is simply taken, no question. No eligible card at all: “Ekstre borcunu sorgulayabileceğiniz uygun bir kredi kartınız bulunmuyor. Sizi ana menüye yönlendiriyorum.”

Notes:
- Digits can come as "dört iki beş üç", "kırk iki elli üç" etc. The assistant maps them to the four digits and moves on. No reading back of the digits, no "… kartınızla devam ediyorum" confirmation; the card name is said anyway at the start of the debt reading.
- Supplementary card holders: they see no eligible card of their own here. Tell them and ask for a different card. (Burcu, is that what the menu does today?)
- If the card name comes back empty from the service, introduce the card by its last four only.

## 4. Reading the debt

Service: `cards.balance` with the chosen card. It returns one block per currency (`debtTL`, `debtUSD`, `debtEUR`, `debtGBP`) with `statementDebt`, `minPayment`, `remainingDebt`, `remainingMinPayment`, `totalDebt`, plus `statementDate`, `lastPayDate`.

Order:
1. Card introduction + statement date (glued to the first currency).
2. Turkish Lira.
3. Dollar, then Euro, then Sterling (only the ones with debt).
4. One sentence for the currencies with no debt.
5. Remaining auto-payment amount, when there is one (**TBD**, see §9).
6. Due date.
7. If the caller has more eligible cards: “Başka bir kartınızın borcunu öğrenmek ister misiniz?”
8. Offer (§5).

Card introduction, example on the Lira line:
“Sonu dört iki beş üç ile biten Yıldız Premium kartınıza ait 21 Ağustos 2026 tarihinde kesilen ekstre Türk Lirası borcunuz …”

### Turkish Lira: three cases by what has been paid

| Paid so far | Sentence |
|---|---|
| Nothing | “Türk Lirası borcunuz XXX TL, ödenmesi gereken minimum tutar ZZZ TL'dir.” |
| Minimum or more | “Türk Lirası borcunuz XXX TL, kalan toplam borcunuz YYY TL'dir. Minimum ödemenizi yaptığınız için teşekkür ederiz.” |
| Less than the minimum | “Türk Lirası borcunuz XXX TL, ödenmesi gereken minimum tutar ZZZ TL, kalan toplam borcunuz YYY TL, kalan minimum ödeme tutarınız TTT TL'dir.” |

XXX statementDebt, ZZZ minPayment, YYY remainingDebt, TTT remainingMinPayment.
How I pick the case (Mert to check): debt only if remainingDebt > 0; "nothing paid" if remainingMinPayment equals or exceeds minPayment; "minimum or more" if remainingMinPayment is zero or below; "less than minimum" otherwise. If remainingDebt is 0,00 we go to the no-debt wording for Lira.

No Lira debt → Lira is skipped and goes into the no-debt sentence.

### Foreign currencies

Same pattern for all three, no paid/unpaid split:

“Dolar borcunuz XXX USD, kalan toplam borcunuz YYY USD, ödenmesi gereken minimum tutar ZZZ USD'dir.”
Euro and Sterling the same way (EUR, GBP; "İngiliz Sterlini borcunuz …").

### Currencies without debt

One sentence at the end. My table (not all 15 lines yet, I'll fill the rest):

| TL | USD | EUR | GBP | Sentence |
|---|---|---|---|---|
| debt | – | – | debt | “Dolar ve Euro borcunuz bulunmamaktadır.” |
| debt | debt | – | – | “Euro ve İngiliz Sterlini borcunuz bulunmamaktadır.” |
| debt | – | debt | – | “Dolar ve İngiliz Sterlini borcunuz bulunmamaktadır.” |
| – | debt | debt | debt | “TL borcunuz bulunmamaktadır.” |
| – | debt | – | – | “TL, Euro ve İngiliz Sterlini borcunuz bulunmamaktadır.” |
| – | – | debt | – | “TL, Dolar ve İngiliz Sterlini borcunuz bulunmamaktadır.” |
| debt | debt | debt | debt | nothing, all four are read |
| … | | | | TBD |

Negative amounts (credit balance) and zero count as "no debt" in that currency. A currency the card does not carry at all: **TBD** whether it goes into this sentence.

### Due date

“Borçlarınız için son ödeme tarihiniz 16 Eylül 2026'dır.” (date from lastPayDate)

If the due date is today, say "bugün": “Borçlarınız için son ödeme tarihiniz bugündür.”

### No statement debt

“Sonu [son 4 hane] ile biten [kart adı] kartınızın [hesap kesim tarihi] tarihli ekstresinden borcunuz bulunmamaktadır. Gelecek dönemler dahil toplam borcunuz GGG TL'dir. Son ödeme tarihiniz [son ödeme tarihi] olacaktır.”

Then the other-card question if there is another eligible card. Otherwise main menu. (Kerem: do we offer e-mail/statement week here too? I lean no, nothing to send.)

### How things are spoken

- Amounts: lira and kuruş in full ("bir milyon iki yüz otuz dört bin beş yüz altmış yedi lira seksen dokuz kuruş"); zero kuruş is dropped ("iki bin beş yüz Türk Lirası"). Dollar/Euro decimals as cents, Sterling as pence.
- Dates: day, month name, year ("21 Ağustos 2026").
- Last four digits one by one: "dört iki beş üç", "bir sıfır sıfır üç". Never "kırk iki elli üç", never "çift sıfır".
- The full card number is never said.
- Every amount and date exactly as the service gave it. Nothing the service did not return is said (no guessing of rates, dates or addresses).

## 5. The offer

After the due date (and after the other-card question when it applies):

“Hesap kesim tarihinizi değiştirebilirim ya da ekstrenizi kayıtlı mail adresinize gönderebilirim.”

Only what the caller can actually do is offered:
- no registered e-mail → only the statement week ("Hesap kesim tarihinizi değiştirebilirim.");
- statement week cannot be changed → only the e-mail;
- neither → no offer.

That means the contact lookup (`contact.email.get`) has to run before the offer, not after the caller picks e-mail. Mert, OK?

**TBD:** we have no way to know in advance whether the caller may still change the week (see §6.2).

Answers:

| Caller says | Goes to |
|---|---|
| e-mail | §6.1 |
| change statement date / week | §6.2 |
| no / nothing else / thanks, bye | main menu, “Sizi ana menüye yönlendiriyorum.” |
| wants to pay | agent, “Borç ödeme işleminiz için sizi müşteri temsilcimize aktarıyorum.” |
| debt + e-mail in the same sentence | read the debt, then go straight to e-mail without the offer question |

## 6. Actions

### 6.1 Statement by e-mail

Only to the address the bank holds. The assistant never takes an address from the caller.

1. `contact.email.get` (customer number). Empty address, or only a phone registered → no suitable e-mail. If the caller asks anyway: “Bankamızda kayıtlı bir e-posta adresiniz bulunmadığı için ekstrenizi gönderemiyorum.” Then statement week if possible, else main menu.
2. Read the address back and ask: “Ekstrenizi … adresine göndermemi ister misiniz?” Readable addresses as they are; long or odd ones shortened ("m ile başlayan Gmail adresiniz"), no spelling letter by letter.
3. Only on a clear yes: `statement.pdf.send` with card, customer number, the registered address and the statement date.
4. “Ekstreniz kayıtlı e-posta adresinize gönderildi.” then “Sizi ana menüye yönlendiriyorum.”

Other answers:
- No → nothing sent, main menu.
- "That address is wrong / I don't use it anymore" → nothing sent; it cannot be changed here; main menu.
- "Send it to another address" → only the registered address is possible.
- "Send last month's" → only the last closed statement.
- Sending again in the same call: max three, then main menu.
- Service error → “Şu anda işleminizi gerçekleştiremiyorum, sizi müşteri temsilcimize aktarıyorum.”

### 6.2 Changing the statement week

Services: `statement.week.get` (current), `statement.week.decide` (preview, changes nothing), `statement.week.change` (the change).

1. Current state: “[kart adı] kartınızın hesap kesim tarihi her ayın [hafta]. haftası olarak tanımlı. Bir sonraki hesap kesim tarihiniz [tarih], son ödeme tarihiniz [tarih]. Hesap kesim tarihinizi değiştirmek ister misiniz?” No → main menu.
   Joint statement: also read the main and the linked card (names, week, next closing and due dates).
2. Options, without the current week: “Hesap kesim tarihinizi ayın 1., 3. ya da 4. haftasına alabilirim. Hangisini tercih edersiniz?”
   - A week or a date we didn't offer → only the offered weeks; read them again.
   - The current week → no change needed.
3. Preview with the chosen week and the current statement day.
4. Confirm: “Yeni hesap kesim haftanız her ayın 3. haftası olacak. Yeni hesap kesim tarihiniz [tarih], son ödeme tarihiniz [tarih] olacak. Onaylıyor musunuz?”
   Joint statement: after the question, add “Bu değişiklik kartınıza bağlı [bağlı kart adı] kartınızı da etkileyecek.”
   - Only a clear "evet" counts. "Olabilir", "sanırım" → ask once more, clearly (three tries).
   - No → no change, “Sizi ana menüye yönlendiriyorum.”
5. `statement.week.change`, only after preview + clear yes.
6. “Sonu [son 4 hane] ile biten [kart adı] kartınızın hesap kesim haftası her ayın 3. haftası olarak değiştirildi. Yeni hesap kesim tarihiniz [tarih], son ödeme tarihiniz [tarih].” Dates from the preview (the change call does not return them). Then main menu.

Any of the three services fails → “Şu anda hesap kesim tarihinizi değiştiremiyorum, sizi müşteri temsilcimize aktarıyorum.”

How often a caller may change: **TBD**. Burcu says the menu has its own limits today; I need the exact rule and whether any service tells us beforehand.

## 7. Exits and general behaviour

| When | Where | Sentence |
|---|---|---|
| Done / nothing else / goodbye after the reading | Main menu | “Sizi ana menüye yönlendiriyorum.” |
| Caller asks for something else mid-flow | Main menu, the request is passed on | “Sizi ana menüye yönlendiriyorum.” |
| Out-of-scope question | Main menu directly | “Size bu konuda yardımcı olamıyorum. Sizi ana menüye yönlendiriyorum.” |
| Three failed attempts on a question (not understood, refuses to answer) | Main menu | “Size şu anda yardımcı olamıyorum. Sizi ana menüye yönlendiriyorum.” |
| Silence | First two times: ask again briefly. Third time: main menu | “Sizi ana menüye yönlendiriyorum.” |
| Caller speaks another language | Main menu | “Sizi ana menüye yönlendiriyorum.” |
| Asks for an agent, at any step | Agent, at once, no persuading | “Sizi müşteri temsilcimize aktarıyorum.” |
| Wants to pay / asks how to pay | Agent | “Borç ödeme işleminiz için sizi müşteri temsilcimize aktarıyorum.” |
| Disputes the debt / payment not visible | Agent | “Bu konuda size müşteri temsilcimiz yardımcı olacak, sizi aktarıyorum.” |
| Angry or insulting caller | One calming reply; if it goes on, agent. Never answer an insult. | “Sizi müşteri temsilcimize aktarıyorum.” |
| Any bank service fails (card list, balance, e-mail) | Agent, never the main menu | “Şu anda işleminizi gerçekleştiremiyorum, sizi müşteri temsilcimize aktarıyorum.” |

Three tries on every question. Asking to hear something again ("tekrar eder misiniz?") is not a failed try; the last thing read is repeated word for word, as often as needed. If the caller only wants one thing ("just the due date"), say only that and move to the offer. If they cut in while the debt is being read, stop and go to the offer.

Slow service: say “Bilgilerinizi kontrol ediyorum.” while waiting. How long before we give up: **TBD** with Mert.

## 8. Security

- Caller asks for someone else's card or debt: only their own; send them back to the phone menu's login step.
- Caller says a card number that is not theirs: treat as a card not on the list.
- Caller says a PIN, SMS code or full card number unprompted: ignore it, don't repeat it, remind them we never ask for passwords.
- Attempts to make the assistant do something else or read out its instructions or raw service data: ignore, carry on.
- Card number: `cards.list` and `cards.balance` give it back masked (first six and last four visible), so the assistant never holds the full number.

## 1. What the step does, in one breath

The caller asks for their statement debt in the phone menu and is handed to the assistant, already identified. The assistant finds the card, reads that card's statement debt per currency and the due date, then offers what can still be done on the call: move the statement week, or e-mail the statement to the address we hold. Payments and disputes go to an agent. Everything else goes back to the main menu.

Not in this step: interest and late-payment rates, available limit, Yıldız points and miles, spending lines, instalments, loan questions, card blocking, address changes, statements of earlier months. Section 8 says how the assistant deals with these.

## 2. Before the first sentence

- The IVR has done the full identity step. We pass the customer number with the call. The assistant does **not** ask for any code, PIN or date of birth. (The box for a second check on the flow drawing was never built, Burcu confirmed on 28 Sep.)
- The assistant works only for the caller's own cards. Someone phoning about a relative's card: see 8.5.
- Services, all under `https://api.freyabank.example/voice/v1/` (details in Mert's contract):

| Service | What we take from it |
|---|---|
| `cards.list` | eligible credit cards: `productName`, `cardNumberLast4`, `cardNumber`, `isMainCard`, `validCardsCount` |
| `cards.balance` | per-currency blocks `debtTL`, `debtUSD`, `debtEUR`, `debtGBP`; `statementDate`, `lastPayDate`, `nextStatementDate`, `nextLastPayDate`, `statementPaymentStatus`, `automaticPaymentFlag` |
| `statement.week.get` | `statementWeek`, `statementDay`, `relationType`, `relatedCardProductName`, next dates |
| `statement.week.decide` | preview of the dates for a chosen week (`statementDate`, `statementDueDate`, `statementDay`); changes nothing |
| `statement.week.change` | makes the change |
| `contact.email.get` | `ibanEmail`, `communicationType` |
| `statement.pdf.send` | sends the statement PDF to the registered address |

- Card numbers: the card number comes back masked from the services (first six and last four visible on the card list). We only ever need the last four for speech, so this is fine for us.
- A `cards.list` answer of "no valid card for this customer" (the 404 warning in Mert's table) is the no-eligible-card case below, not a broken service. A 500 or a timeout is a broken service.

## 3. Card

### 3.1 Picking the card

1. Call `cards.list`.
2. No eligible card: “Ekstre borcunu sorgulayabileceğiniz uygun bir kredi kartınız bulunmuyor. Sizi ana menüye aktarıyorum.” End.
3. One eligible card: it is the card. No question, go to the debt.
4. More than one: “Hangi kartınızın borcunu öğrenmek istersiniz? Örneğin, [kart adı] veya [kart adı] diyebilirsiniz.” At most two examples, and only names from this caller's own list. Never a card name the caller does not have.
5. If the caller already said a card name when they arrived and it fits exactly one card, skip the question and read that card.

Once the card is settled there is no "carrying on with your … card" line and no "is that right?". The card name comes at the start of the reading anyway.

### 3.2 Two cards with the same name

Reworked on 7 Oct, three steps:

| Step | When | Assistant says |
|---|---|---|
| a | two or more cards with the name the caller gave | “[kart adı] isimli birden fazla kartınız var. Kartınızın son dört hanesini söyler misiniz?” e.g. “Yıldız isimli birden fazla kartınız var. Kartınızın son dört hanesini söyler misiniz?” |
| b | the last four are the same on two cards too | “Son dört hanesi 4253 olan birden fazla kartınız var. Kartınızın son altı hanesini söyler misiniz?” (caller's own four digits in place of 4253) |
| c | the last six are the same as well | “Son altı hanesi aynı olan birden fazla kartınız var. Kart numaranızı söyler misiniz?” |

Then read the debt of the card that matches.

(Mert: with the masked list I'm not sure step b can tell two cards apart in every case. Leaving the step in, please check.)

### 3.3 When the answer doesn't settle the card

- **Name half-said or described** (a colour, "the travel one", only the brand): if it fits several cards, read back just those names; if it fits none, read all the names again, and that uses up one try. A card we don't have on the list at all (another bank's, one that's been closed): tell them there's no card under that name and read the eligible ones again.
- **"All of them, please":** we can't, the balance service works one card at a time. Put the selection question from 3.1 again; this costs a try just like an answer we can't use, and when the three are gone: “Size şu anda yardımcı olamıyorum. Sizi ana menüye aktarıyorum.”
- **Digits:** however the caller says them (digit by digit, in pairs, as one big number), we turn them into the four digits, e.g. 4253, and go straight to that card's debt. Wrong digits or "I don't have the card on me": ask again (for the digits, or for the card name if they can't give digits), three tries, then the main menu. If they read out the whole card number we find the card from it. Whatever they said, four digits, six or all sixteen, the assistant does not say it back to them.
- **Switching:** a caller who picks a card and then wants a different one goes back to selection. After a reading, a question about another of their cards also goes back to selection, and we read that second card.
- **Supplementary card only** (`isMainCard` false): tell them there is no eligible card for this and ask them to choose a different one.
- **No product name from the service:** the card is introduced by its last four only, “Sonu 4253 ile biten kartınıza ait …”

## 4. Reading the debt

### 4.1 Order

Kerem and I agreed this order on 7 Oct; it is the order for every reading:

1. Card introduction and the statement closing date
2. Turkish Lira debt
3. Dollar, then Euro, then İngiliz Sterlini debts
4. The currencies with no debt, in one sentence
5. Remaining automatic payment amount (only when it applies, 4.6)
6. Due date
7. "Another card?" question, if the caller has more than one eligible card
8. The offer (section 5), with only the options the caller can actually use

### 4.2 Card introduction and the closing date

Every reading opens with “Sonu [son 4 hane] ile biten [kart adı]”, every time, also on the second card in the same call. The closing date goes at the start of the **first** currency that is read:

“Sonu 9012 ile biten Yıldız Miles Platinum kartınıza ait 21 Ekim 2025 tarihinde kesilen ekstre Türk Lirası borcunuz …”

If there is no Turkish Lira debt, the same opening goes in front of the first foreign currency instead.

### 4.3 Turkish Lira

Pick the sentence by what the caller has paid since the statement (fields from `debtTL`):

| Case | Rule | Sentence |
|---|---|---|
| Nothing paid | `remainingMinPayment` > 0 and equal to or above `minPayment` | “Türk Lirası borcunuz XXX TL, ödenmesi gereken minimum tutar ZZZ TL'dir.” |
| Minimum or more paid | `remainingDebt` > 0 and `remainingMinPayment` is 0 or less | “Türk Lirası borcunuz XXX TL, kalan toplam borcunuz YYY TL'dir. Minimum ödemenizi yaptığınız için teşekkür ederiz.” |
| Less than the minimum paid | `remainingMinPayment` > 0 and below `minPayment` | “Türk Lirası borcunuz XXX TL, ödenmesi gereken minimum tutar ZZZ TL, kalan toplam borcunuz YYY TL, kalan minimum ödeme tutarınız TTT TL'dir.” |
| No Turkish Lira debt | `remainingDebt` is 0.00 or below | Skip Turkish Lira, go to the foreign currencies. Turkish Lira then goes into the no-debt sentence (4.5). |

XXX `statementDebt`, ZZZ `minPayment`, YYY `remainingDebt`, TTT `remainingMinPayment`.

Edges, because Ozan asked: remaining minimum exactly equal to the minimum → "nothing paid". Remaining minimum exactly zero → "minimum paid". Remaining debt 0,00 → no debt in that currency.

### 4.4 Foreign currencies

One pattern, same for all three, read Dolar → Euro → İngiliz Sterlini:

“Dolar borcunuz XXX USD, kalan toplam borcunuz YYY USD, ödenmesi gereken minimum tutar ZZZ USD'dir.”

Euro and İngiliz Sterlini use the same sentence with their own name and code. No paid / not-paid split for foreign currency.

When some foreign currency debt has been moved over into the Turkish Lira debt (`transferAmount` above zero on that currency's block), the caller should hear which currency that was before the Turkish Lira figures. Ozan, could you draft the line? (Kerem to give me the cases where this really happens; I have seen two in production this year.)

### 4.5 Currencies with no debt

One sentence for all of them together, after the foreign currency lines. If all four have debt, nothing is said here. If none of the four has statement debt, this sentence is not used at all: it is the no-debt reading (4.7).

A currency whose block is missing or empty in `cards.balance` (the card simply doesn't have it) is **left out** of this sentence.

Burcu's menu only had six of these. Grouped by how many currencies are clear:

| No debt in | Assistant says |
|---|---|
| (none, all four owe) | nothing |
| one: Türk Lirası | “Türk Lirası borcunuz bulunmamaktadır.” |
| one: Dolar | “Dolar borcunuz bulunmamaktadır.” |
| one: Euro | “Euro borcunuz bulunmamaktadır.” |
| one: İngiliz Sterlini | “İngiliz Sterlini borcunuz bulunmamaktadır.” |
| two: Türk Lirası, Dolar | “Türk Lirası ve Dolar borcunuz bulunmamaktadır.” |
| two: Türk Lirası, Euro | “Türk Lirası ve Euro borcunuz bulunmamaktadır.” |
| two: Türk Lirası, İngiliz Sterlini | “Türk Lirası ve İngiliz Sterlini borcunuz bulunmamaktadır.” |
| two: Dolar, Euro | “Dolar ve Euro borcunuz bulunmamaktadır.” |
| two: Dolar, İngiliz Sterlini | “Dolar ve İngiliz Sterlini borcunuz bulunmamaktadır.” |
| two: Euro, İngiliz Sterlini | “Euro ve İngiliz Sterlini borcunuz bulunmamaktadır.” |
| three: Türk Lirası, Dolar, Euro | “Türk Lirası, Dolar ve Euro borcunuz bulunmamaktadır.” |
| three: Türk Lirası, Dolar, İngiliz Sterlini | “Türk Lirası, Dolar ve İngiliz Sterlini borcunuz bulunmamaktadır.” |
| three: Türk Lirası, Euro, İngiliz Sterlini | “Türk Lirası, Euro ve İngiliz Sterlini borcunuz bulunmamaktadır.” |
| three: Dolar, Euro, İngiliz Sterlini | “Dolar, Euro ve İngiliz Sterlini borcunuz bulunmamaktadır.” |

Fifteen rows, fourteen sentences. It is "Türk Lirası" in these, never "TL" (see 4.9).

### 4.6 Remaining automatic payment

Only when the due date has passed, the card has an automatic payment instruction (`automaticPaymentFlag` "Y") and `remainAutomaticPaymentAmount` is above zero: the assistant tells the caller how much of the automatic payment is still to be taken, in Turkish Lira. Comes after the no-debt sentence and before the due date.

### 4.7 No statement debt

When `statementPaymentStatus` is NO_DEBT:

“Sonu [son 4 hane] ile biten [kart adı] kartınızın [hesap kesim tarihi] tarihli ekstresinden borcunuz bulunmamaktadır. Gelecek dönemler dahil toplam borcunuz GGG TL'dir. Son ödeme tarihiniz [son ödeme tarihi] olacaktır.”

Then, if the caller has another eligible card: “Başka bir kartınızın borcunu öğrenmek ister misiniz?” Yes → card selection. No, or no other card → main menu.

(Open with Kerem: do we also read the future-period total in foreign currency here, or Turkish Lira only? Today's sentence only has GGG TL. Deniz also suggested making the offer before the main menu in this branch; not agreed yet.)

### 4.8 Due date

“Borçlarınız için son ödeme tarihiniz [son ödeme tarihi]'dir.” (suffix follows the date: 26 Ekim'dir, 1 Kasım'dır …)

If the due date is today, say "bugün" instead of the date: “Borçlarınız için son ödeme tarihiniz bugündür.”

### 4.9 How to say things

- Currency names in full, never the code: TL → Türk Lirası, USD → Dolar, EUR → Euro, GBP → İngiliz Sterlini. This also covers the TL inside the sentences above.
- Turkish Lira amounts: lira and kuruş in full. 1.234.567,89 → “bir milyon iki yüz otuz dört bin beş yüz altmış yedi lira seksen dokuz kuruş”. Big amounts with kuruş are no exception.
- Zero kuruş is not said: 2.500,00 → “İki bin beş yüz Türk Lirası”, never "sıfır kuruş".
- Foreign currency decimals as cent (Dolar, Euro) and peni (İngiliz Sterlini): 7.666,50 USD → “Yedi bin altı yüz altmış altı dolar elli sent”.
- Dates as day, month name, year: 21.10.2025 → “21 Ekim 2025”.
- Last four digits one by one: 4253 → “dört iki beş üç”, 1003 → “bir sıfır sıfır üç”. Not "çift sıfır", not "kırk iki elli üç".
- The full card number is never said, under any circumstance.
- Every amount and date read is exactly what `cards.balance` returned. 1.000 is not rounded to anything, kuruş is not dropped, currencies are not mixed up. If a figure did not come from a service, the assistant does not say it.

### 4.10 Odd values and odd days

- A minus figure means the bank owes the customer; it is never read out as debt. That currency counts as clear, and so does one at exactly 0,00 (it goes into the "borcunuz bulunmamaktadır" sentence).
- A card so new that no statement has been cut yet: tell them there is no debt, and don't invent a date to go with it.
- Phoning on the day the statement is cut: tell them the cut is today and happens at 00.00, then give the total debt. Something like “Hesap kesim tarihiniz bugün, ekstreniz saat 00.00 itibarıyla kesilecek.”
- From the cut date up to the due date: the normal statement reading (4.2 to 4.8).
- After the due date: say it has passed, then give the total debt.
- Due date today: the "bugün" sentence in 4.8.

## 5. After the reading

### 5.1 Another card first

Callers with more than one eligible card get “Başka bir kartınızın borcunu öğrenmek ister misiniz?” **before** the offer. Yes → card selection (3.1) and read that card. When there are no cards left or they say no, go to the offer.

### 5.2 The offer

Only offer what this caller can do. For that we call `contact.email.get` **before** the offer (not after the caller asks for the mail, which is how I had it in September).

| Registered e-mail | Statement week change still possible this year | Offer |
|---|---|---|
| yes | yes | “Hesap kesim tarihinizi değiştirebilirim ya da ekstrenizi kayıtlı mail adresinize gönderebilirim.” |
| no | yes | “Hesap kesim tarihinizi değiştirebilirim.” |
| yes | no | “Ekstrenizi kayıtlı mail adresinize gönderebilirim.” |
| no | no | no offer |

"No registered e-mail" = `ibanEmail` empty, or `communicationType` is phone only. In every case the caller can still say they want nothing else, which takes them to the main menu.

(Whether the yearly change right is already used: Mert has asked the card platform for a flag, no answer yet. See open points.)

### 5.3 What the caller answers

| Answer | Goes to |
|---|---|
| wants the statement mailed | 6 |
| wants to move the statement week | 7 |
| nothing else, thanks, that's all | main menu, “Sizi ana menüye yönlendiriyorum.” |
| wants to pay, or asks how/where to pay | agent, “Borç ödeme işleminiz için sizi müşteri temsilcimize aktarıyorum.” |

## 6. Statement by e-mail

What it does: the PDF of the card's most recent statement goes to the e-mail address on file with us. No customer data changes. Once it's out we can't call it back, so we need a clear go-ahead.

1. Registered address: already fetched for the offer (5.2). If there isn't one, the e-mail option is never offered. If the caller asks for it anyway: “Bankamızda kayıtlı bir e-posta adresiniz bulunmadığı için ekstrenizi gönderemiyorum.” Then offer the statement week change if they still have the right, otherwise main menu.
2. Ask: “Ekstrenizi … adresine göndermemi ister misiniz?” A short, readable address is read as it is. A long or messy one is shortened, e.g. “m ile başlayan Gmail adresiniz”. Never spelled letter by letter.
3. Only after a clear yes, call `statement.pdf.send`, and only ever with the registered address.
4. Success: “Ekstreniz kayıtlı e-posta adresinize gönderildi.” then “Sizi ana menüye yönlendiriyorum.”

Things that came up in the session:
- A no, or "that address isn't mine any more": nothing goes out. In the second case also tell them we can't change the address on this call. Both end with “Sizi ana menüye yönlendiriyorum.”
- Another address, a month further back, a paper copy: we only send the most recent statement, and only to the address on file. Paper and text message aren't something this step does; say so and go to the main menu.
- Asked to send it again: fine, up to three times in one call, then “Sizi ana menüye yönlendiriyorum.”
- `contact.email.get` or `statement.pdf.send` fails (error, timeout, "document not found"): “Şu anda işleminizi gerçekleştiremiyorum, sizi müşteri temsilcimize aktarıyorum.”

## 7. Changing the statement week

Moves the card's statement closing week, which moves the next closing date and due date. Permanent; cannot be undone in the call.

How often: **once per calendar year** (Kerem, 7 Oct). Before the week question the assistant may say “Hesap kesim tarihinizi yılda bir kez değiştirebilirsiniz.” Elçin is fine either way, it is not a must. A caller who has used the right this year is not offered the change; if they ask anyway, the same sentence is how we explain why it can't be done.

Steps:

1. `statement.week.get`. Error: “Şu anda hesap kesim tarihinizi değiştiremiyorum, sizi müşteri temsilcimize aktarıyorum.”
2. Tell and ask: “[kart adı] kartınızın hesap kesim tarihi her ayın [hafta]. haftası olarak tanımlı. Bir sonraki hesap kesim tarihiniz [tarih], son ödeme tarihiniz [tarih]. Hesap kesim tarihinizi değiştirmek ister misiniz?” No → main menu.
   Joint statement (`relationType` main or linked): read both cards here: each card's last four and name, the payment week, the next closing date and next due date.
3. Options, without the current week. For a card in week 2: “Hesap kesim tarihinizi ayın 1., 3. ya da 4. haftasına alabilirim. Hangisini tercih edersiniz?”
4. Preview: `statement.week.decide` with the chosen week and the card's current `statementDay` from step 1. It doesn't change the card. Error: same sentence as step 1.
5. Joint statement only, before the question in step 6: “Bu değişiklik kartınıza bağlı [bağlı kart adı] kartınızı da etkileyecek.” If the caller holds the linked card, say instead that the change also moves the main card it hangs off, e.g. “Bu değişiklik kartınızın bağlı olduğu [asıl kart adı] kartınızı da etkileyecek.”
6. Confirm, with the preview dates: “Yeni hesap kesim haftanız her ayın 3. haftası olacak. Yeni hesap kesim tarihiniz [tarih], son ödeme tarihiniz [tarih] olacak. Onaylıyor musunuz?” Only a clear "evet" counts.
7. Only now, after the preview and the clear yes: `statement.week.change`. Error: same sentence as step 1.
8. Done: “Sonu [son 4 hane] ile biten [kart adı] kartınızın hesap kesim haftası her ayın 3. haftası olarak değiştirildi. Yeni hesap kesim tarihiniz [tarih], son ödeme tarihiniz [tarih].” Dates are the ones from the preview. Then “Sizi ana menüye yönlendiriyorum.”

Around the choice and the yes:
- The caller can only pick from the weeks we read out. A day of the month, a date, any week we didn't offer: read the options again. Their current week: tell them nothing needs changing.
- A no at step 6 means no change and “Sizi ana menüye yönlendiriyorum.” Something hedged ("perhaps", "I suppose") is not a yes: ask once more, plainly, three tries in all, until we get a clear "evet".
- If, after step 8, they want it undone: tell them the change has already gone through. If they ask from when it applies: the new closing date from the preview.
- `statement.week.change` failing after a good preview is a service error like any other: step 1's sentence, agent.

## 8. Edge cases (whole call)

Reworked after 7 Oct. Applies at every step unless a section above says otherwise.

### 8.1 Tries

Three tries per question, whatever the question. When the third is gone: “Size şu anda yardımcı olamıyorum. Sizi ana menüye aktarıyorum.” A try is lost on a mumble, an answer to some other question, or a flat refusal to say. A request to hear something again is not a try: read the same thing again, as often as they like.

What the caller came here for, we finish here. Not understanding the caller is never a reason to put them through to an agent; the only transfers are the ones in 8.3 and 8.4.

### 8.2 Silence

Changed on 7 Oct. First and second silence: ask the question again, shorter. Third silence: “Sesinizi alamadığım için görüşmeyi sonlandırıyorum.” and the call is closed. No main menu here.

### 8.3 Agent

- The caller asks for a person, at any point: put them through at once, no tries, no persuading. “Sizi müşteri temsilcimize aktarıyorum.” (Transfer on the first ask for now; Burcu wants to look at this again after go-live.)
- Paying, or how and where to pay: “Borç ödeme işleminiz için sizi müşteri temsilcimize aktarıyorum.”
- The caller says the debt is wrong, or that a payment they made isn't showing: “Bu konuda size müşteri temsilcimiz yardımcı olacak, sizi aktarıyorum.”
- Upset, raising their voice, swearing: up to three calming replies. Still complaining after the third: “Sizi müşteri temsilcimize aktarıyorum.” Insults are never returned.
- Any Freya Bank service failing (error or no answer) goes to an agent, never to the main menu: “Şu anda işleminizi gerçekleştiremiyorum, sizi müşteri temsilcimize aktarıyorum.” For the statement week services it is the statement week sentence in section 7. The `cards.list` "no valid card" warning is not a failure (section 2).
- A slow service: “Bilgilerinizi kontrol ediyorum.” and keep waiting. How long before we call it a failure is open; Deniz is coming back with a number. Mert says some answers take more than ten seconds and still succeed.

### 8.4 Main menu

- The sentence for now: “Sizi ana menüye yönlendiriyorum.” Burcu wants to look at it again once the call routing piece is live. Until then “Sizi ana menüye aktarıyorum.” and “Başka hangi konuda yardımcı olabilirim?” are also fine where they appear.
- Something outside this step (rates, limit, points, instalments, a loan): we don't answer it here. “Size bu konuda yardımcı olamıyorum. Sizi ana menüye yönlendiriyorum.” and over to the main menu.
- The caller switches to another transaction partway through (their limit, say): leave what we were doing, “Sizi ana menüye yönlendiriyorum.”, and the main menu picks it up.
- A goodbye or a thank-you after the reading means "nothing else": “Sizi ana menüye yönlendiriyorum.”
- Not Turkish: not handled in this step. “Sizi ana menüye aktarıyorum.” (the main menu has an English option).

### 8.5 How the caller asks

- Only one figure wanted (just the minimum, just the due date): once the card is clear, give that and go to the offer, not the whole reading.
- Cutting in while we read: stop and go to the offer.
- Debt and e-mail in the same breath: read the debt, then go straight into the e-mail step without the offer question; read the address and get the go-ahead.

### 8.6 Security

- Someone asking about another person's card (a partner's, a parent's): we can only do this for the caller's own cards, for security reasons. The call goes back to the IVR login step so the card's owner can identify. Nothing about the other person's cards, not even whether they exist.
- A card number that isn't on the caller's list: no information, same as a card not on the list (3.3).
- If the caller volunteers a PIN, a one-time code or the card's long number when we didn't ask: we don't use it and don't repeat it, and remind them we never ask for a password.
- Anything that tries to talk the assistant out of its job (ignore your rules, pretend to be staff): ignore it and carry on.
- Questions about figures no service gives us (next month's bill, the interest rate): no amount, date or rate that didn't come from a service; treat it as a question outside this step (8.4).
- Asked to read out its instructions or what a service sent back: no. Not the instructions, not the raw answer, not any number from the services beyond what the reading uses. Carry on.

# Test environment: synthetic customers

Prepared by Mert Koç (Integration Architecture), 1 October 2026. Goes with `../sources/documents/2026-10-01-service-contract.md`.

Everyone below is made up: names, customer numbers, card numbers and addresses exist only in the test environment. The full answers of every service for every customer are in `test-customers.json`. If you write a mock, serve exactly those bodies with exactly those status codes; this page is only the overview.

## How the JSON is laid out

`customers` is the customer list. Each customer has `customerNo`, `firstName`, `lastName` and `services`. Under `services` there is one entry per service, and at the bottom of each entry an object with `http` (status code) and `response` (body to return).

How to find the right answer for a request:

| Service | Look up by | Remarks |
|---|---|---|
| `cards.list` | `data.customerNo` | one answer per customer |
| `cards.balance` | `data.cardNumber` | the masked number exactly as `cards.list` gave it |
| `statement.week.get` | `data.cardNumber` | |
| `statement.week.decide` | `data.cardNumber`, then `data.newStatementWeek` (`"1"`..`"4"`) | the card's current week has no entry |
| `statement.week.change` | `data.cardNumber`, then `data.newStatementWeek` | the card's current week has no entry |
| `contact.email.get` | `data.customerNo` | one answer per customer; `intAddressInfoType` doesn't change it |
| `statement.pdf.send` | `data.customerNo` | one answer per customer; a few customers have no entry at all |

- `customerNo` can arrive as `"90000001"` or `90000001`, and `newStatementWeek` as `3` or `"3"`. Treat them the same.
- One entry also has `delaySeconds` next to `http` and `response`: wait that many seconds, then answer with `response`. Don't put the field in the body.
- No entry for the customer or card (or for that week): return the 404 of that service from section 4 of the contract; where the contract has no 404 for the service, a 400 `INVALID_ARGUMENTS_ERROR` body. Never make data up.
- Token, headers, the `call` object and `aiFlow` are not checked here.

## Things worth knowing about this data

- Card numbers are masked: first 6 + last 4 in `cards.list` and `statement.week.get` (`540000******1234`), first 4 + last 4 in the `cards.balance` answer (`5400********1234`). Only the first six and last four digits exist in this data; nothing else is there to match against.
- Some customers have two cards with the same product name and the same last four digits, which differ only in the first six.
- Some cards share a statement with another card (`relationType` `M` / `C` in `statement.week.get`): customers 92220795, 95960044 and 97974112.
- A few cards have no `debtGBP` block in `cards.balance`.
- Product names come straight from the card system as free text; one is empty.
- Dates are fixed in the data (`dd.MM.yyyy`). Amounts are numbers with a dot as decimal separator.
- A successful `statement.pdf.send` returns `data.exitState` `"DONE"`.

# Tools and code

This page describes how a workflow calls HTTP APIs and runs Python. Read [workflow-format.md](workflow-format.md) first.

Statements marked "verified in a working builder" come from a builder that created a 6-node workflow through the REST API. The workflow has code nodes, `api_call` tools, post-hooks and transitions on tool results. Its agent passed its practice cases. Statements marked "seen in a trial call" come from the event log of a simulation call made with that builder.

## Tool function shape

Every external action is a **tool function**. The shape is the same wherever you attach it.

```json
{
  "type": "function",
  "config": { "timeoutMs": 10000, "maxRetries": 2 },
  "function": {
    "name": "lookup_order",
    "handler": "__function__:api_call",
    "description": "Look up one order. CALL it when the caller asks about a specific order.",
    "parameters": {
      "type": "object",
      "properties": {
        "url": { "type": "string", "default": "https://api.example.com/v1/orders/lookup" },
        "method": { "type": "string", "default": "POST" },
        "headers": {
          "type": "object",
          "properties": { "Content-Type": { "type": "string", "default": "application/json" } }
        },
        "body": {
          "type": "object",
          "properties": {
            "customer_id": { "type": "string", "default": "{{customer_id}}" },
            "order_number": { "type": "string", "description": "Order number, digits only", "default": "{{order_number}}" }
          },
          "required": ["order_number"]
        }
      }
    }
  },
  "response_mapping": [
    { "path": "data.status", "variable": "order_status" }
  ]
}
```

| Field | Meaning |
|---|---|
| `type` | Always `"function"` |
| `function.name` | Tool name. The model calls it by this name. Result variables are named after it |
| `function.handler` | Which runtime executes the tool. See the table below |
| `function.description` | Read by the dialogue model when the tool is in `tools`. Ignored in `pre_actions` |
| `function.parameters` | JSON-schema object. `properties` holds the parameters |
| `config.timeoutMs` | Timeout of one attempt, in milliseconds |
| `config.maxRetries` | Tool-level retries of a failed call |
| `config.interruptible` | `false` makes the tool run in the background. See "Background tools" |
| `config.alwaysRunsAt` | Makes the tool a lifecycle tool. See "Lifecycle tools" |
| `response_mapping` | Tool level, for tools in `tools`. Maps the result to variables |
| `pre_process_code` | Python hook that runs before the call |
| `post_process_code` | Python hook that runs after the call |

| Handler | Runs |
|---|---|
| `__function__:api_call` | An HTTP request |
| `__function__:code_exec` | A Python snippet in a sandbox |
| `__function__:end_call` | Hangs up. Used in the `terminal` of an `end_call` node |

Handlers for integrations, knowledge search, call transfer and rescheduling also exist. They are not needed here.

`api_call` parameters:

| Parameter | Meaning |
|---|---|
| `url` | Request URL. `{{var}}` works |
| `method` | HTTP method |
| `headers` | Object. Each header is a property with a `default` |
| `body` | Object. Each body field is a property under `body.properties` |
| `connect_retries` | Transport retries. See "Retries and timeouts" |

## How a parameter gets its value

One key decides, per parameter: `default`.

| Declaration | Who supplies the value | Does the model see the parameter |
|---|---|---|
| `default` with a literal, or with a `{{var}}` that has a value | The workflow. The value is **baked** | No |
| `default` with a `{{var}}` that has no value when the node is entered | The model | Yes, named after the variable, with the property's `type`, `description` and `enum` |
| no `default` | The model | Yes |
| `const` | Nobody. `const` does **not** bake | It only constrains the model's own output |

Rules:

- **Use `default` for fixed backend config** such as `url`, `method` and auth headers. At registration the engine moves every `default` into the tool's base config, resolves `{{var}}` from the variable table, and removes the field from the schema the model sees.
- **Never use `const` for a value you want sent.** The engine reads only `default`. A `{{var}}` inside a `const` never resolves. An `api_call` whose `url` is a `const` fails with "URL is required".
- **Baking happens when the node is entered.** A `{{var}}` default is resolved against the variable table at that moment.

The working builder uses this for every tool: `customer_id` has `"default": "{{customer_id}}"` and is baked from a call variable. Every other body field has `"default": "{{<field name>}}"`, where no variable of that name exists, so the model fills it. Verified in a working builder.

Seen in a trial call: the model's arguments are stored as `<tool>_args.<field>` in the variable table, for example `lookup_order_args.order_number`. They were not stored under the bare field name.

Take care that a model-filled field does not share its name with a variable that is already set when the node is entered. The value would be baked and the model would never see the parameter.

### `api_call` body field rules

- Declare each body field as a leaf under `body.properties.<field>`.
- Put the field's `type`, `description` and `enum` on that leaf. Put required fields in `body.required`.
- Give each leaf its own `default`.
- Do not put a field spec at the top level of `parameters.properties` next to a `body.default` template object. The engine looks for the spec at `body.properties.<field>`, does not find it, and the model sees only "Template variable: name". The `enum` and `description` are lost while the call still works.
- A body that exists only as one `body.default` object also shows as an empty form in the dashboard editor. Saving from there removes the tool.

A `code_exec` tool is different: its parameters are true top-level arguments. Declare a model-filled one as a top-level property without `default`.

### When a baked variable has no value

| Field type | Variable unset | Variable is `""` |
|---|---|---|
| Normal field in an engine-run call (`pre_actions`, lifecycle tool) | The field is dropped from the request. No error | The field is sent empty |
| `code` of `code_exec` | The literal text `{{var}}` stays in the Python source and the snippet crashes | |

Fix: make sure an earlier node always sets the variable, even to a sentinel value. In code, read variables from `vars` and do not splice them in with `{{var}}`.

### Constrain model-filled parameters

When a value must be one of a known set, do not use a free string. The model sometimes invents a value that looks plausible.

- Use an `enum` on the leaf, and list the values in the `description` as well.
- Or use a `number` that is an index into a list, with the valid range in the description. A pre-hook or the backend turns the index into the real value.
- If neither is possible, name the exact source in the description and tell the model to copy the value unchanged.

```json
{
  "type": "object",
  "properties": {
    "queue": {
      "type": "string",
      "description": "Team that takes over. One of: billing, delivery, returns.",
      "enum": ["billing", "delivery", "returns"],
      "default": "{{queue}}"
    }
  },
  "required": ["queue"]
}
```

## `pre_actions` versus `tools`

The placement decides who fires the call.

| Placement | Node type | Who calls it | When |
|---|---|---|---|
| `pre_actions` | `api_request`, `code` | The engine | On node entry, before any model turn |
| `tools` | `conversation` | The dialogue model | During a turn, when the model decides to |
| Workflow-level `tools` with `config.alwaysRunsAt` | none | The engine | At call start or call end |

The platform removes `tools` from non-conversation nodes and `pre_actions` from conversation nodes. It does so without an error: the JSON you sent looks fine, the create call succeeds, and the stored node has an empty array. A node cannot use both.

**Use `pre_actions`** when the call must always run and the model has nothing to decide. Example: after the order number is known, always fetch the order.

**Use `tools`** when the call depends on what the user says. Example: cancel the order only if the caller asks for it.

Differences in behaviour:

| | `pre_actions` | `tools` |
|---|---|---|
| Can be skipped | No | Yes. The model may not call it if the description and the prompt do not push for it |
| Timing | Node entry | Inside a turn. The model can call a tool, speak, then call another |
| Result in the conversation | A tool call and tool result pair is added to the history | The same |
| `response_mapping` lives | On the **node** | On the **tool** |
| `description` | Ignored | The only text the model reads about the tool |

To run a fixed call before a tool-driven conversation, use a passthrough `api_request` node and transition from it into the conversation node. Do not build a long chain of passthrough nodes for optional actions. Put those into one conversation node with several tools.

### A `pre_actions` node

```json
{
  "name": "fetch_order",
  "node_type": "api_request",
  "passthrough": true,
  "passthrough_default_transition": "present",
  "on_enter": { "type": "silent" },
  "pre_actions": [
    {
      "type": "function",
      "config": { "timeoutMs": 10000, "maxRetries": 2 },
      "function": {
        "name": "get_order",
        "handler": "__function__:api_call",
        "description": "Get the order.",
        "parameters": {
          "type": "object",
          "properties": {
            "url": { "type": "string", "default": "https://api.example.com/v1/get_order" },
            "method": { "type": "string", "default": "POST" },
            "headers": { "type": "object", "properties": { "Content-Type": { "type": "string", "default": "application/json" } } },
            "body": { "type": "object", "properties": { "order_number": { "type": "string", "default": "{{order_number}}" } }, "required": [] }
          }
        }
      }
    }
  ],
  "response_mapping": [
    { "path": "data.items", "variable": "items" }
  ],
  "transitions": [
    { "target_node": "present", "description": "always", "condition": { "operator": "always" } }
  ]
}
```

The last `always` transition is mandatory. A passthrough node with no matching transition deadlocks.

### Tool descriptions

In `tools`, the `description` decides whether the model calls the tool.

- Write it as an instruction with the trigger: "CALL it every time the caller gives an order number."
- A plain description such as "Looks up an order" lets the model acknowledge the request in words and never call the tool. That is the most common failure of nodes with many tools.
- If two tools could match, say which one not to use and name the other.
- In `task_message`, put the tool rules before long reference text and state: when a rule says to use a tool, call the tool.
- The working builder also tells the model to call one tool per message and to speak after every tool result. Verified in a working builder. In a trial call a model turn with no text and no tool call produced the error event "The model returned no speakable content".

A tool is available only in the nodes that list it. Seen in a trial call: the model called a tool that the current node did not list. The result was the text "The function `<name>` is not currently available."

## `response_mapping`

`response_mapping` copies values from a call result into named variables. It needs no model call.

```json
{
  "response_mapping": [
    { "path": "data.status", "variable": "order_status" },
    { "path": "data.items", "variable": "items" }
  ]
}
```

| Field | Meaning |
|---|---|
| `path` | Dot path into the tool result |
| `variable` | Name of the variable to set |

### Placement

- For a tool in `tools`: inside the tool object, next to `function` and `config`.
- For `pre_actions`: at the **node level**. A `response_mapping` nested inside a `pre_actions` entry is ignored and the variable never appears.

`extraction_schema` follows the same placement rule if you use it on a call result.

### Where a result lands (trial findings)

Seen in a trial call: the result of an `api_call` is an envelope around the HTTP response.

```json
{
  "status": "success",
  "data": { "ok": true, "verified": true, "attempts_left": 3 },
  "message": "Successfully executed POST request",
  "status_code": 200,
  "header": { "Content-Type": "application/json" }
}
```

`data` is the JSON body the API returned. `header` holds the HTTP response headers.

The engine also writes every result into the variable table by itself, flattened with dots. You do not need a mapping for these. For a tool named `check_answer` whose API returned `{"ok": true, "verified": true, "attempts_left": 3}`, the trial call's variable table held:

| Variable | Value |
|---|---|
| `check_answer_args.<field>` | Each argument the model sent |
| `check_answer_response.status` | `success` |
| `check_answer_response.data.ok` | `true` (a string) |
| `check_answer_response.data.verified` | `true` (a string) |
| `check_answer_response.data.attempts_left` | `3` |
| `check_answer_response.message` | `Successfully executed POST request` |
| `check_answer_response.status_code` | `200` |
| `check_answer_response.header.<Header-Name>` | One variable per response header |
| `check_answer_status_code` | `200` |
| `check_answer_success_count` | Number of successful calls so far |

Each call of the same tool overwrites the previous `_args` and `_response` values.

### Which mapping paths work

- **Start the path at the envelope, with `data.`**. If the API returns `{"ok": true}`, map `data.ok`. If it returns `{"products": [...]}`, map `data.products`. Verified in a working builder, on a tool-level mapping and on a node-level mapping.
- A path without the `data.` prefix (for the same body: `ok`) is not confirmed. A smaller example builder uses it. In an early trial call the mapped variables stayed unset and the transitions on them never fired. The mapping paths of that call are not recorded. The builder that passed uses `data.` paths.
- The flattened key can be used directly as a transition variable: `check_answer_response.data.verified`. Verified in a working builder, which tests the mapped variable and the flattened key in the same OR group as a safeguard.
- Booleans arrive as strings. The trial call showed `true` in lower case in the flattened keys. Test both `"true"` and `"True"`, or map a string field.
- A mapped list or object: the exact form it has later inside `vars` is not confirmed. The working builder reads it defensively. It accepts a list, a JSON string, and flattened keys.

## Routing on tool results

Routing runs again after a tool result arrives. A transition on a result variable fires in the same turn, before any further model turn. Seen in a trial call.

```json
{
  "transitions": [
    {
      "target_node": "load_order",
      "description": "The check passed",
      "condition": {
        "logic": "or",
        "conditions": [
          { "variable": "check_passed", "operator": "equals", "operand": "true" },
          { "variable": "check_passed", "operator": "equals", "operand": "True" },
          { "variable": "check_answer_response.data.verified", "operator": "equals", "operand": "true" },
          { "variable": "check_answer_response.data.verified", "operator": "equals", "operand": "True" }
        ]
      }
    }
  ]
}
```

Rules:

- On a passthrough node, end with an `always` transition so that a failed or empty response does not deadlock.
- Use a tool result to leave a conversation node. The pattern "a closing tool sets a variable, a transition on that variable leads to an `end_call` node" is verified in a working builder.
- To leave a node that carries out an action, do not re-test the user's earlier intent with `matches_intent`. The router looks at the latest user message and can route away before the tool was called. Extract a follow-up enum with a default such as `stay`, and branch with `equals`.

### Success and failure counters

The engine keeps two integer variables per call target. No mapping is needed.

| Placement | Variables |
|---|---|
| `pre_actions` node | `<nodeId>_success_count`, `<nodeId>_failure_count` |
| Tool in `tools` with handler `api_call` | `<toolName>_success_count`, `<toolName>_failure_count` |

Seen in a trial call: `check_answer_success_count` was `2` after two successful calls, and a code node named `setup` produced `setup_success_count` with the value `1`.

```json
{
  "transitions": [
    { "target_node": "give_up", "description": "The lookup failed three times", "condition": { "logic": "or", "conditions": [ { "variable": "lookup_order_failure_count", "operator": "greater_than", "operand": 2 } ] } },
    { "target_node": "ask_again", "description": "always", "condition": { "operator": "always" } }
  ]
}
```

### `suppress_tool_results`

A node-level boolean for nodes that run API calls. With `true` the dialogue model sees only a short `{status: "success"}` summary in place of the raw response. Variables are still mapped and routing still sees them. Use it for large responses, or when the mapped variables already hold everything the model needs.

### Background tools

A tool with `"config": {"interruptible": false}` runs in the background. A user interruption does not cancel it. Its result arrives one or more turns later. The mapped variables, the `_response` keys and the counters are filled as usual, but not in the same turn. A transition that reads them right after the call can find them unset. Gate on the variable with `is_set`.

## Retries and timeouts

| Setting | Where | Default | What it does |
|---|---|---|---|
| `timeoutMs` | `config` | not documented | Time limit of one attempt, in milliseconds |
| `maxRetries` | `config` | not documented | Tool-level retries after a failed response |
| `connect_retries` | `parameters.properties`, as a baked parameter | `2` | Retries when the connection could not be established |
| `timeout_ms` | `code_exec` parameter | `30000` | Time limit of a code snippet |

`connect_retries` in detail:

- It retries only failures to establish the connection: connection refused, or reset during the TCP or TLS handshake. The request never reached the server, so a repeat is safe even for POST.
- HTTP error statuses and timeouts are not retried by it.
- Hard cap `5`. `0` means a single attempt.
- Back-off is 150 ms times the attempt number, with a new connection each time.
- All attempts share one 30 second budget for the request.
- Declare it next to `url` and `method`: `"connect_retries": {"type": "number", "default": 0}`. It is not a `config` field.

The working builder sets `maxRetries` to `0` on tools that write data and to `2` on its read-only `pre_actions` call. A retried write can record the same thing twice if the API is not idempotent.

## Pre and post Python hooks

An `api_call` tool can carry two Python snippets. They run on the server, in a sandbox, right before and right after the call. They are top-level fields of the tool object.

```json
{
  "type": "function",
  "config": { "timeoutMs": 10000, "maxRetries": 0 },
  "function": {
    "name": "check_answer",
    "handler": "__function__:api_call",
    "description": "Check one answer. CALL it every time the caller answers the question.",
    "parameters": {
      "type": "object",
      "properties": {
        "url": { "type": "string", "default": "https://api.example.com/v1/check_answer" },
        "method": { "type": "string", "default": "POST" },
        "body": { "type": "object", "properties": { "answer": { "type": "string", "description": "The caller's answer", "default": "{{answer}}" } }, "required": ["answer"] }
      }
    }
  },
  "pre_process_code": "vars['member_code'] = str(vars.get('member_code') or '').strip().upper()",
  "post_process_code": "try:\n    if isinstance(result, dict):\n        result.pop('header', None)\n        d = result.get('data')\n        if isinstance(d, dict):\n            d['what_to_do_next'] = 'Ask the next question.' if d.get('verified') else 'Ask the same question again.'\nexcept Exception:\n    pass\n"
}
```

| Hook | Names available | Use |
|---|---|---|
| `pre_process_code` | `vars`: mutable dict that fills the `{{var}}` placeholders of the request. `config`: the substituted request with `url`, `method`, `headers`, `body` | Clean a value, or rewrite the whole request |
| `post_process_code` | `result`: the tool result, mutable | Reshape, shorten or extend the result |

Documented behaviour:

- The post-hook runs before `response_mapping` and extraction see the result.
- An empty or whitespace-only string means no hook.
- Hooks are honoured only on `api_call` tools (and on the integration and knowledge search handlers). The platform removes them from any other handler when the workflow is saved.
- In a pre-hook, setting `config['body']` to a string sends that string as the raw body, with no JSON encoding. Set the `Content-Type` header yourself in that case.

### What `result` looks like in a post-hook

The internal reference shows `result` as the response body. A working builder shows otherwise. Verified in a working builder:

- For an `api_call`, `result` is the envelope described above: a dict with `status`, `data`, `message`, `status_code` and `header`. The API's JSON body is `result["data"]`.
- A key that the hook adds inside `result["data"]` reaches the dialogue model as part of the tool result. The working builder adds a `what_to_do_next` sentence there, and its prompt tells the model to obey it.
- `result.pop("header", None)` removes the response headers. The working builder does this on every tool, so that headers do not take up space in the model's context.
- Mapping paths still start with `data.` when a post-hook is present.

The working builder writes every hook inside `try` and `except Exception: pass` and checks types with `isinstance` before use. What the platform does when a hook raises is not documented.

Seen in a test on 10 October: a post-hook can read call variables and write new variables, and a later pre-hook reads them. Not confirmed: whether a change to `result` also changes the flattened `<tool>_response.*` variables.

## Code nodes and `code_exec`

A `code` node runs a Python snippet when it is entered. The snippet is a `code_exec` function in `pre_actions`.

```json
{
  "name": "compute_delivery",
  "node_type": "code",
  "passthrough": true,
  "passthrough_default_transition": "tell_delivery",
  "on_enter": { "type": "silent" },
  "pre_actions": [
    {
      "type": "function",
      "function": {
        "name": "code_exec",
        "handler": "__function__:code_exec",
        "parameters": {
          "type": "object",
          "properties": {
            "code": { "type": "string", "default": "import datetime\ntry:\n    start = datetime.date.fromisoformat(str(vars.get('shipped_on'))[:10])\n    eta = start + datetime.timedelta(days=3)\n    vars['delivery_day'] = eta.isoformat()\n    vars['delivery_state'] = 'known'\nexcept Exception:\n    vars['delivery_day'] = ''\n    vars['delivery_state'] = 'unknown'\n" },
            "timeout_ms": { "type": "number", "default": 10000 }
          }
        }
      }
    }
  ],
  "transitions": [
    { "target_node": "tell_delivery", "description": "always", "condition": { "operator": "always" } }
  ]
}
```

| Parameter | Meaning |
|---|---|
| `code` | The Python source, as a baked `default` string |
| `timeout_ms` | Time limit in milliseconds. Default `30000` |

### Reading and writing variables

- The snippet gets a dict named `vars`. It holds the current workflow variables.
- Read with `vars.get("name")`. A variable that was never set is absent.
- Write with `vars["name"] = value`. Every key the snippet assigns becomes a workflow variable.

Verified in a working builder:

- Call variables are in `vars`. The builder reads `vars.get("now")`, a call variable passed with the simulation.
- The result of an earlier `api_request` node is reachable from `vars` in a later code node. The builder looks for it under the mapped variable name first and under the flattened result keys second. Which of the two held the data is not recorded.
- A string written to `vars["date_facts"]` in a code node resolves as `{{date_facts}}` in the `task_message` of later conversation nodes. Multi-line strings work.
- The standard modules `json`, `re` and `datetime` can be imported.
- The same snippet can run in two code nodes at different points of the call. The later run sees the variables added in between.

### What a code node returns

Seen in a trial call: the result of a successful `code_exec` is

```json
{ "status": "success", "data": null, "message": "Code executed successfully", "status_code": 200 }
```

The snippet's output is not in `data`. Its values reach the workflow only through `vars`. After a code node named `setup` ran, the variable table held:

| Variable | Value |
|---|---|
| each key the snippet wrote, for example `date_facts` | the value, with source `tool_result` and source node `setup` |
| `setup_response.status` | `success` |
| `setup_response.data` | `null` |
| `setup_response.message` | `Code executed successfully` |
| `setup_response.status_code` | `200` |
| `setup_status_code` | `200` |
| `setup_success_count` | `1` |

For a code node the automatic keys are named after the **node**, not after `code_exec`.

### Rules for snippets

- **Do not write `{{` or `}}` in the code.** The internal sources disagree on whether the `code` field is templated. One says it is exempt. Another says placeholders are resolved when the code runs and an unset one is left as literal text, which breaks the Python. The working builder removes every `{{` and `}}` from generated code (a nested dict literal such as `{'a': {'b': 1}}` ends in `}}`) and reads all values from `vars`.
- **Never let a snippet raise.** Wrap the body in `try` and `except`, and write a fallback value for every variable that a later prompt or condition reads. A prompt that references an unset variable shows the literal placeholder to the model.
- **Write strings for routing flags**, such as `known` and `unknown`. Do not route on a Python boolean. See "Do not route on a boolean" in workflow-format.md.
- Keep snippets fast. They block the conversation.
- Do arithmetic, date calculation and counting in code, and give the model the finished facts as text. Verified in a working builder: it computes a block of date facts in a code node and places it in the prompts.
- Treat a code node like an API node: `passthrough: true`, a `passthrough_default_transition`, and a last `always` transition.

### Sandbox limits

| Limit | Value |
|---|---|
| Time | `timeout_ms`, default `30000` |
| Modules | `json`, `re` and `datetime` are verified in a working builder. The full list is not documented |
| Network and file access | Not documented |
| Memory and output size | Not documented |

### `code_exec` as a tool

`code_exec` can also be a tool in the `tools` array of a conversation node, called by the model. Its parameters are top-level arguments, declared without `default` so the model fills them. For such a tool the `code` field resolves `{{var}}` when the tool is called, against the current variable table. The working builder does not use this form, so nothing about it is verified here.

## Lifecycle tools

A tool whose `config.alwaysRunsAt` is a non-empty list is never shown to the model. The engine fires it at a fixed point of the call.

| Value | When |
|---|---|
| `start_of_call` | During call setup, before the first turn |
| `end_of_call` | After the call has ended |
| `each_turn` | Accepted by the schema but not implemented. It never fires |

Put a lifecycle tool that must run on every call into the workflow's top-level `tools` array.

```json
{
  "initial_node": "greeting",
  "nodes": {},
  "tools": [
    {
      "type": "function",
      "config": { "alwaysRunsAt": ["end_of_call"] },
      "function": {
        "name": "push_call_result",
        "handler": "__function__:api_call",
        "parameters": {
          "type": "object",
          "properties": {
            "url": { "type": "string", "default": "https://api.example.com/v1/call-results" },
            "method": { "type": "string", "default": "POST" },
            "body": {
              "type": "object",
              "properties": {
                "summary": { "type": "string", "default": "{{call.analysis.summary}}" },
                "reason": { "type": "string", "default": "{{call.call_end_reason}}" }
              }
            }
          }
        }
      }
    }
  ]
}
```

Rules:

- A workflow-level tool without `alwaysRunsAt` never runs and the model never sees it.
- A lifecycle tool in a node's `tools` runs for `start_of_call` only on the `initial_node`, and for `end_of_call` only on the node in which the call ended.
- If a `{{var}}` parameter is still unresolved, one model call fills the parameters. If everything resolves, the handler runs directly.
- `response_mapping` is applied for `start_of_call`. It is not applied for `end_of_call`.
- At the end of a call the order is: call analysis, then `end_of_call` tools, then success-criteria judging. An `end_of_call` tool can use `{{call.analysis.summary}}`, `{{call.analysis.structured_data_str}}`, `{{call.call_end_reason}}`, `{{call.call_end_reason_category}}`, `{{call.call_tags}}` and `{{call.duration}}`.
- A malformed lifecycle tool is dropped at run time without an error. Validate with a dry run (api.md).

## Tool results and the next turn

After a tool call returns, the model sees the result and has to produce the next turn itself. Two things were seen in practice runs with the hackathon's agent model:

- **The agent says nothing after the tool call.** The result arrives, no assistant message follows, and the simulated customer hangs up after waiting. It happens more often when the result is bare data such as `{"ok": true, "verified": true}`.
- **The agent ignores a negative result.** For example it reads `"verified": false` and moves on to the next question as if the answer had passed.

What fixed both in a working builder (verified, see the post-hook section above): a post-hook on the tool that adds one plain instruction line to the result before the model sees it, for example a `what_to_do_next` field that says what the answer means and what to say or call next. The model then has something to act on.

Also say it in the step's prompt: after every tool result, speak to the customer or call the next tool. Never end a turn with nothing.

## Checklist

- Fixed values use `default`, never `const`.
- Each `api_call` body field is a leaf under `body.properties` with its own `default`, `description` and `enum`.
- `tools` only on `conversation` nodes. `pre_actions` only on `api_request` and `code` nodes.
- `response_mapping` on the tool for `tools`, on the node for `pre_actions`.
- Mapping paths start with `data.`.
- Booleans from results are tested as `"true"` and `"True"`, or replaced by string fields.
- Every passthrough node ends with an `always` transition.
- Code reads and writes through `vars`, never raises, and contains no `{{` or `}}`.
- Tool descriptions say when to call the tool.

# Workflow format

This page describes the workflow JSON that defines a Freya agent. Read it before you write a builder. Tools, API calls and code are in [tools-and-code.md](tools-and-code.md). The REST calls are in [api.md](api.md).

Some statements are marked "verified in a working builder". Those come from a builder that created a 6-node workflow through the REST API and whose agent passed its practice cases.

## What a workflow is

A workflow describes a conversation as a graph. Each **node** is one step of the conversation and has its own prompt. **Transitions** move the conversation from one node to the next. A transition fires on what the user said or on the value of a variable.

When you create a workflow through the API, the platform creates an agent for it. You run simulations against that agent.

## Three model calls per turn

After each user message the platform makes three separate model calls. They do not share a prompt.

```text
user message
    |
    v
1. EXTRACTION   reads the message, stores variables
2. ROUTING      decides whether to leave the node
3. DIALOGUE     writes the agent's reply
```

| Call | What it sees | What it produces |
|---|---|---|
| Extraction | Recent conversation messages and the current node's `extraction_schema` | Variable values |
| Routing | Recent conversation messages and the transition descriptions. It does not see the dialogue prompt | The transition to take, or none |
| Dialogue | `system_prompt`, `role_message`, `task_message`, the full conversation history, and the node's `tools` | The reply, or a tool call |

Consequences:

- A routing instruction inside `task_message` has no effect on routing. Routing reads only transitions.
- The dialogue model can call only the tools in the current node's `tools` array. Everything else (API calls on entry, code, ending the call) is run by the workflow engine.
- Deterministic conditions (variable checks) need no model call. They are evaluated in code.

## Top-level keys

```json
{
  "initial_node": "greeting",
  "system_prompt": "You are the assistant of a dental clinic. Speak English.",
  "nodes": {},
  "global_nodes": {},
  "test_variables": { "customer_id": "c_test" }
}
```

| Key | Type | Required | Meaning |
|---|---|---|---|
| `initial_node` | string | yes | Key of the node where every call starts |
| `nodes` | object | yes | Map of node key to node definition |
| `system_prompt` | string | no | Global rules. Part of the dialogue prompt in every node |
| `global_nodes` | object | no | Interrupt handlers that can fire from any node. See "Global nodes" |
| `test_variables` | object | no | Default values for call variables. See "Variables" |
| `context_variables` | object | no | A state block of chosen variables for the dialogue model. See "Context variables" |
| `tools` | array | no | Workflow-level lifecycle tools. See tools-and-code.md |
| `agent_config` | object | no | Model and call settings. See below |
| `nodePositions` | object | no | Layout for the visual editor. The working builder omits it |

**`agent_config`**: omit it. The platform fills in defaults. It holds model, voice and timeout settings that a builder for this event does not need. In a simulation you choose the models with the override fields described in api.md.

**No `null` values.** The schema is strict. Leave an optional field out, or set an optional string to `""`. A `null` fails validation.

The REST API takes the workflow inside a request body `{"name": "...", "workflow": {...}}`. The object described on this page is the value of `workflow`.

## Node types

| `node_type` | Purpose | Speaks to the user | Carries |
|---|---|---|---|
| `conversation` | A dialogue step | yes | `task_message`, `tools`, `extraction_schema`, `transitions` |
| `api_request` | Runs an HTTP call on entry | usually not | `pre_actions`, node-level `response_mapping`, `transitions` |
| `code` | Runs a Python snippet on entry | usually not | `pre_actions` with a `code_exec` function, `transitions` |
| `end_call` | Ends the call | optional farewell | `terminal` |

Other node types exist: `transfer_call`, `integration`, `knowledge_base`, `reschedule_call`, `invoke_agent`, `exit`. Telephony, voice settings, knowledge base and integrations also exist on the platform. You do not need any of them here and this page does not describe them.

The platform strips fields that do not belong to a node type, without an error:

- `tools` is kept only on `conversation` nodes.
- `pre_actions` is kept only on `api_request` and `code` nodes (and the other non-conversation action types).

So a node cannot have both. If a call must run before a conversation node, put it in its own `api_request` node in front.

## Node fields

| Field | Type | Default | Meaning |
|---|---|---|---|
| `name` | string | | Node name. Use the same value as the node's key, in `snake_case` |
| `node_type` | string | | One of the types above |
| `task_message` | string | | The instruction for the dialogue model in this node |
| `role_message` | string | | Extra persona text for this node. Rarely needed |
| `on_enter` | object | `{"type": "llm"}` | What happens on entry. See "Entry behaviour" |
| `on_enter_first_entry_only` | boolean | `false` | Run the entry behaviour only on the first visit |
| `transitions` | array | | Outgoing transitions, in priority order |
| `routing_prompt` | string | | Extra context for the routing model in this node |
| `loop_condition` | string | | Intent description for staying in the node. See "Loop conditions" |
| `loop_prompt` | string | | Replaces `task_message` from the second turn in the node |
| `extraction_schema` | array | | Variables to extract from user speech in this node |
| `tools` | array | | Tools the dialogue model may call. `conversation` nodes only |
| `pre_actions` | array | | Calls the engine runs on entry. `api_request` and `code` nodes |
| `response_mapping` | array | | For `pre_actions` nodes: maps the call result to variables. Node level |
| `passthrough` | boolean | `false` | Route right after entry, without waiting for the user |
| `passthrough_default_transition` | string | | Target node for a passthrough node |
| `max_node_turns` | integer | `10` | Cap on user turns spent in the node |
| `max_turn_transition` | string | | Target node when the cap is reached |
| `terminal` | object | | The end-call function. `end_call` nodes only |
| `disable_inactivity_monitor` | boolean | `false` | Switch off silence check-ins for this node |
| `suppress_tool_results` | boolean | `false` | Hide raw call results from the dialogue model. See tools-and-code.md |
| `truncation_strategy` | string | `keep_all` | How much history the dialogue model sees. See "Limits" |
| `truncation_window_size` | integer | `10` | Number of recent messages kept by `keep_recent` and `summarize` |
| `reasoning_override` | string | `auto` | `enabled` or `disabled` forces model reasoning on or off for this node. Only models that support such a switch react to it |

A per-node `idle_config` (silence timeouts) and per-node speech settings also exist. They matter on voice calls only.

## Prompts

The dialogue model receives one system message built from three parts:

```text
system_prompt        workflow level, the same in every node
role_message         node level, optional
## Current Task
task_message         node level, what to do now
```

| Field | Level | Use it for |
|---|---|---|
| `system_prompt` | workflow | Identity, language, tone, rules that hold in every node |
| `role_message` | node | A different persona for one node. Most workflows leave it out |
| `task_message` | node | What the agent must do in this step |
| `loop_prompt` | node | A replacement for `task_message` after the first turn in the node |
| `on_enter` | node | What the agent does when it enters the node |

Rules for `task_message`:

- Write instructions for the model, not a script.
- Cover this node's job only.
- Do not describe routing or name other nodes. The model does not know about nodes. Text such as "then move to the lookup node" makes it narrate steps that have not happened.
- If the node has tools, refer to them by name and say when to call them. Do not repeat the tool descriptions.
- In a node without tools, state that no tool call is allowed in this turn. If the node has a `loop_prompt`, put that rule in both prompts.

Example:

```json
{
  "name": "collect_details",
  "node_type": "conversation",
  "task_message": "Ask which service the caller wants and on which day. Ask one question at a time. If the caller is unsure about the day, offer to check the next free days.",
  "transitions": []
}
```

### Entry behaviour

| `on_enter` | Behaviour |
|---|---|
| `{"type": "llm"}` | The model writes the first line from `task_message`. Default. An optional `prompt` key overrides the entry instruction for this node |
| `{"type": "tts", "text": "..."}` | A fixed line is spoken. No model call. `{{var}}` works in `text` |
| `{"type": "silent"}` | Nothing is said. The node waits for the user, or routes at once if it is a passthrough node |
| `{"type": "audio", "asset_id": "..."}` | Plays a recorded asset. Not needed here |

Set `on_enter_first_entry_only` to `true` when a node can be re-entered and must not repeat its opening line. This works better than a prompt rule such as "do not greet twice".

### History across nodes

When the conversation moves from node A to node B:

- User and assistant messages are kept.
- The system message is replaced by node B's prompts.
- A loop prompt from node A is removed.

So node B can refer to anything said earlier. Variables also stay for the whole call.

## Variables

All variables live in one table for the whole call. There is no per-node scope. A variable is never cleared on a transition. A later write with the same name overwrites it.

| Source | How it gets in |
|---|---|
| Call variables | Passed when the call or simulation starts |
| `test_variables` | Workflow-level defaults for call variables |
| Extraction | `extraction_schema` on a node |
| Call results | `response_mapping`, and the automatic result keys described in tools-and-code.md |
| Code | A code node or `code_exec` tool writes into `vars` |
| System | Set by the platform |

### `{{var}}` substitution

Write `{{variable_name}}` in prompts, `on_enter.text`, transition descriptions, URLs, headers and request bodies. The engine replaces it before the model or the HTTP call sees the text.

| Form | Result |
|---|---|
| `{{customer_name}}` | The value as a string |
| `{{amount:json}}` | The value JSON-encoded. Use it inside request bodies |

Behaviour to know:

- Date values are formatted for speech in the agent's language when they are substituted into a prompt.
- An unresolved variable in a prompt stays as the literal text `{{variable_name}}`. The model sees the placeholder. In a fixed spoken line (`on_enter.text`, a terminal `spoken_message`) the agent says it aloud.
- In a field of an engine-run call (a `pre_actions` call or a lifecycle tool) an unresolved placeholder behaves in two ways. If the value is exactly one placeholder (`"{{x}}"`), the whole field is dropped from the request. If the value mixes text and a placeholder (`"Status: {{x}}"`), the request goes out with the literal `{{x}}` in it.
- Do not reference a variable in a mixed value unless an earlier node always sets it.

### Call variables and `test_variables`

Call variables are the inputs of one call, for example a customer id or the current time. In a simulation you pass them per persona in `customerVariablesMap` (see api.md).

`test_variables` is a top-level object of default values. On a web call to the workflow it is merged into the call variables. A value passed with the call wins over a test variable of the same name.

```json
{
  "test_variables": {
    "customer_id": "c_test",
    "first_name": "Dana",
    "now": "2026-03-11T10:00"
  }
}
```

Verified in a working builder: call variables are readable as `{{customer_id}}` in prompts and tool parameters, and as `vars.get("customer_id")` in code.

### System variables

| Variable | Example | Meaning |
|---|---|---|
| `{{system.iso_utc_now}}` | `2026-03-11T14:30:00Z` | UTC timestamp of call start |
| `{{system.todays_date_en_cst}}` | `11 March 2026 Wednesday 08:30` | English date, UTC-6 |
| `{{system.todays_date_en_est}}` | `11 March 2026 Wednesday 09:30` | English date, UTC-5 |
| `{{system.todays_date_tr}}` | | Turkish date with day name and time, UTC+3 |
| `{{system.todays_date_tr.iso_8601}}` | `2026-03-11` | ISO date, UTC+3 |
| `{{system.conversation}}` | `AGENT: hello\nUSER: hi` | Transcript so far |
| `{{system.conversation.last-N}}` | | Last N turns. N is `1`, `5`, `10` or `20` |
| `{{call.direction}}` | `web` | `inbound`, `outbound`, `web` or `simulation`. A chat simulation in the trial showed `web` |
| `{{call.duration}}` | `42` | Whole seconds since call start |
| `{{call.call_id}}` | | Platform call id |
| `{{<node>.current_turns}}` | `2` | User turns in the node since the last entry. Resets on every transition |
| `{{<node>.total_turns}}` | `5` | User turns in the node over the whole call |

There is no `{{current_date}}` placeholder. These system dates are the real clock. If your task supplies its own "now" as a call variable, use that variable.

`{{system.conversation.last-N}}` is useful in a transition description or a `routing_prompt` when the routing model needs more than the last message.

### Context variables

Warning from a test on 10 October: a workflow saved over the API came back without this key, and the save gave no error. Do not rely on it. Write the values the model needs into the prompt with `{{variable}}` instead.

`context_variables` is a top-level key. It shows chosen variables to the dialogue model as a state block, so you do not have to write variable tables into prompt text.

```json
{
  "context_variables": {
    "pre_history_description": "Static call context",
    "post_history_description": "Live state",
    "items": [
      { "name": "customer_tier", "placement": "pre_history", "description": "Customer tier" },
      { "name": "attempt_count", "placement": "post_history" }
    ]
  }
}
```

| Field | Meaning |
|---|---|
| `items[].name` | Name of a variable in the variable table. Must match `^[a-zA-Z_]\w*$` and be unique across both placements |
| `items[].placement` | `pre_history` or `post_history` |
| `items[].description` | Optional label |
| `pre_history_description`, `post_history_description` | Heading text of each section |

Rules:

- An item points at a variable. It does not create one. If nothing sets the variable, the row is skipped without an error.
- `pre_history` is written once into the system prompt. Use it only for values that never change during the call.
- `post_history` is rendered again on every turn after the chat history and is not stored in the history. Use it for values that change.
- The block is rendered as `<CONTEXT_VARIABLES>`, one line `- name (description): value` per populated item.
- No other keys are allowed on an item. There is no `value`, `type` or `default`.
- It does not affect extraction or tool parameter substitution.

## Transitions

A transition is an object in a node's `transitions` array.

| Field | Type | Meaning |
|---|---|---|
| `target_node` | string | Key of the next node. May be the node itself. `__previous__` is allowed in global nodes |
| `description` | string | What the transition is for. The routing model reads it |
| `condition` | object | When the transition fires |
| `is_tool_call` | boolean | The dialogue model triggers the transition by calling a tool. See "Tool-call transitions" |

### Condition operators

Deterministic operators check a variable in code. No model call.

| Operator | Needs | True when |
|---|---|---|
| `equals` | `variable`, `operand` | `str(value) == str(operand)` |
| `not_equals` | `variable`, `operand` | The inverse of `equals` |
| `greater_than` | `variable`, `operand` | `float(value) > float(operand)` |
| `less_than` | `variable`, `operand` | `float(value) < float(operand)` |
| `contains` | `variable`, `operand` | `operand` is a substring of the value, ignoring case |
| `is_set` | `variable` | The variable has any value |
| `is_not_set` | `variable` | The variable has no value |
| `always` | nothing | Always |

The semantic operator uses the routing model.

| Operator | Needs | True when |
|---|---|---|
| `matches_intent` | `description` | The routing model judges that the user's last message matches the description |

All `matches_intent` conditions of one evaluation are judged in a single model call.

### Condition shapes

An unconditional transition:

```json
{ "target_node": "next_step", "description": "always", "condition": { "operator": "always" } }
```

An intent condition:

```json
{
  "target_node": "complaint",
  "description": "The user wants to complain",
  "condition": { "operator": "matches_intent", "description": "The user is unhappy or wants to file a complaint" }
}
```

Variable conditions go inside a group. The top-level group always uses `"logic": "or"`:

```json
{
  "target_node": "order_found",
  "description": "The lookup returned an order",
  "condition": {
    "logic": "or",
    "conditions": [
      { "variable": "order_status", "operator": "equals", "operand": "shipped" },
      { "variable": "order_status", "operator": "equals", "operand": "delivered" }
    ]
  }
}
```

For AND, nest a group inside the top-level OR. Never put `"logic": "and"` at the top level.

```json
{
  "target_node": "priority_desk",
  "description": "Gold customer with a late order",
  "condition": {
    "logic": "or",
    "conditions": [
      {
        "logic": "and",
        "conditions": [
          { "variable": "customer_tier", "operator": "equals", "operand": "gold" },
          { "variable": "days_late", "operator": "greater_than", "operand": 3 }
        ]
      }
    ]
  }
}
```

The working builder uses the bare form for `always` and the grouped form for every variable check. The internal reference also shows a bare single variable condition (`{"variable": ..., "operator": ..., "operand": ...}`) directly under `condition`.

### Do not route on a boolean

`equals` compares strings. A boolean can arrive as `"True"` or as `"true"`, depending on how it was written into the table. A mismatch fails silently: the branch never fires and nothing reports an error.

- Prefer a string value such as `verified` or `rejected`, written by your code or by the API.
- If you must test a boolean that comes from an API response, test both spellings. Verified in a working builder:

```json
{
  "target_node": "wrap_up",
  "description": "The booking call succeeded",
  "condition": {
    "logic": "or",
    "conditions": [
      { "variable": "booking_ok", "operator": "equals", "operand": "true" },
      { "variable": "booking_ok", "operator": "equals", "operand": "True" }
    ]
  }
}
```

`greater_than` and `less_than` convert both sides to numbers, so `2` and `"2"` behave the same. Use them for counters.

### Order of evaluation

After each user message, routing runs in this order. The first match wins and routing stops.

```text
1. loop_condition of the current node    match: stay in the node, use loop_prompt
2. the node's transitions, in list order match: go to target_node
3. global nodes                          match: enter the global node
4. nothing matched                       stay in the node, wait for the next user message
```

Within step 2:

- Transitions are checked in list order. Put specific conditions first and broad ones last.
- Deterministic conditions are evaluated first. If one matches, no routing model call is made.
- If several transitions of a node have the same `target_node`, the engine merges them at load time into one transition. Its condition is the OR of the originals. If one of them is unconditional, the merged transition is unconditional.

Routing also runs after a tool result arrives. Verified in a working builder: a transition on a variable that a tool's `response_mapping` sets fires in the same turn, without a further user message.

When nothing matches, there is no fallback. The agent stays and answers from the same `task_message`. Make sure every realistic path has a matching transition.

### `routing_prompt`

A node-level string. It replaces the default intent-matching instruction of the routing model for this node. Use it when the transition descriptions cannot carry the rule, for example "stay here until both the name and the date are given".

### Self-transition

A last transition with `always` that targets the node itself keeps the user in the node until an earlier transition matches.

```json
{ "target_node": "collect_details", "description": "Keep collecting", "condition": { "operator": "always" } }
```

Prefer this to `loop_condition` in most cases. All routing then lives in one ordered list.

### Loop conditions

`loop_condition` is an intent description. The routing model checks it before all transitions. When it matches, the agent stays in the node.

`loop_prompt` replaces `task_message` in the system message from the second turn in the node. The model sees one of the two, never both. Write it so that it stands alone. `{{var}}` works in it, so it can show what was already collected.

```json
{
  "name": "collect_contact",
  "node_type": "conversation",
  "task_message": "Ask for the caller's full name and email address.",
  "loop_condition": "The user has not yet given both a full name and an email address",
  "loop_prompt": "Name so far: {{customer_name}}. Email so far: {{email}}. Ask only for what is still missing. When both are present, read them back once.",
  "transitions": []
}
```

Make the loop condition specific. "The user has not finished" matches everything and the agent never leaves.

### Tool-call transitions

Set `is_tool_call` to `true` on a transition. The dialogue model then sees the transition as a tool named `transition_to_<node>` and triggers it by calling that tool. The router does not evaluate it after each turn.

```json
{
  "target_node": "confirm_booking",
  "description": "The caller accepted the offered slot",
  "is_tool_call": true,
  "condition": { "operator": "matches_intent", "description": "The caller accepted the offered slot" }
}
```

Use it when the agent should decide to move, for example because of something it just said or computed. The agent can acknowledge and move in the same message. The target node's `on_enter` then asks the next question. Global nodes accept the same flag.

### Passthrough nodes

A node with `"passthrough": true` routes right after its entry actions. It does not wait for the user. `api_request` and `code` nodes are normally passthrough nodes.

- Set `passthrough_default_transition` to the next node.
- End `transitions` with an `always` transition. A passthrough node with no matching transition deadlocks.
- Set `on_enter` to `{"type": "silent"}`, or to a short fixed line that covers the wait.

```json
{
  "name": "prepare",
  "node_type": "code",
  "passthrough": true,
  "passthrough_default_transition": "greeting",
  "on_enter": { "type": "silent" },
  "pre_actions": [],
  "transitions": [
    { "target_node": "greeting", "description": "always", "condition": { "operator": "always" } }
  ]
}
```

Verified in a working builder: a passthrough `code` node can be the `initial_node`. It runs before the agent says anything.

### Global nodes

A global node is an interrupt handler. It can fire from any node. It is checked only after the current node's own transitions found no match.

A global node has the same fields as a normal node, plus:

| Field | Meaning |
|---|---|
| `condition` | When the global node activates. Same format as a transition condition |
| `description` | Purpose of the node |
| `excluded_nodes` | Array of node keys where it must not fire |
| `is_tool_call` | Offer the global node to the dialogue model as a tool, not as a per-turn check |

`__previous__` as a `target_node` or as `passthrough_default_transition` returns to the node that was interrupted.

```json
{
  "global_nodes": {
    "off_topic": {
      "name": "off_topic",
      "description": "Brings the caller back to the subject",
      "condition": { "operator": "matches_intent", "description": "The user talks about something unrelated to their order" },
      "task_message": "Redirect the caller to the subject.",
      "on_enter": { "type": "tts", "text": "I can only help with your order. Let us continue." },
      "passthrough": true,
      "passthrough_default_transition": "__previous__",
      "excluded_nodes": ["goodbye"],
      "transitions": [
        { "target_node": "__previous__", "description": "always", "condition": { "operator": "always" } }
      ]
    }
  }
}
```

Rules:

- List terminal nodes in `excluded_nodes`, or the global node can loop.
- Exclude nodes where an interrupt would do harm, for example an identity check.
- For a plain redirect use a passthrough node with a fixed line. It is faster and more predictable than a model reply.
- Use global nodes for interrupts that can happen anywhere. Do not copy the same transition into every node.

## Extraction schema

`extraction_schema` is an array on a node. After each user message the extraction model fills the listed variables from the conversation.

```json
{
  "extraction_schema": [
    {
      "name": "order_number",
      "type": "string",
      "description": "The order number the caller reads out",
      "validation_pattern": "^[0-9]{8}$",
      "max_retries": 2,
      "min_confidence": 0.8
    },
    {
      "name": "request_type",
      "type": "string",
      "enum_values": ["status", "cancel", "change_address", "other"],
      "description": "What the caller wants to do with the order",
      "min_confidence": 0.7
    }
  ]
}
```

| Field | Type | Meaning |
|---|---|---|
| `name` | string | Variable name |
| `type` | string | `string`, `integer`, `float`, `boolean`, `date`, `datetime`, `name`, `phone_number` |
| `description` | string | What the variable is |
| `enum_values` | array | Allowed values. Works on every type. The old `enum` type is deprecated and becomes `string` |
| `extraction_prompt` | string | A custom extraction template. See the warning below |
| `validation_pattern` | string | Regular expression the value must match |
| `min_confidence` | number | 0.0 to 1.0. Values below it are discarded. Default `0.95` |
| `max_retries` | integer | Retries after a failed validation, with the error given to the model |

How it works:

1. The extraction model sees recent messages and the schema.
2. It returns structured values.
3. Confidence is computed from the model's token probabilities, not from a self-report.
4. Each value is checked against `validation_pattern` and `enum_values`.
5. On failure the model retries, up to `max_retries`.

Rules:

- **Set `min_confidence` on every variable.** The default of 0.95 is strict. A discarded value leaves no trace in the transcript, so it looks the same as "nothing was extracted".
- **`extraction_prompt` replaces the whole built-in template.** It is not appended. A custom prompt must contain the input placeholders itself: `{{extractor.speech}}`, `{{extractor.conversation.last-10}}`, `{{extractor.type_preamble}}` and `{{extractor.variables_list}}`. Without them the extractor never sees the user's message and returns nothing on every turn, while dialogue and routing look healthy.
- **Declare dates as `type: "date"`.** The date types give the extractor today's date and the rules for relative dates such as "tomorrow". A date typed as `string` gets no date anchor and the model guesses the year.
- The built-in date rules turn vague expressions such as "next week" into a concrete date. If you need vague dates rejected, a custom prompt must say so and state that this overrides the general rules.
- No `null`. Omit optional fields or use `""`.
- An extracted variable is available to the same node's transitions in the same turn, and to every later node.

Inside `extraction_prompt` these date placeholders resolve: `{{date.today}}`, `{{time.now}}`, `{{date.day_of_week}}`, `{{date.yesterday}}`, `{{date.tomorrow}}`, `{{date.day_after_tomorrow}}`, `{{date.next_week}}`, `{{date.end_of_month}}`, `{{date.first_next_month}}`, `{{date.next_mon}}` to `{{date.next_sun}}`, `{{date.last_mon}}` to `{{date.last_sun}}`, `{{date.fnm_mon}}` to `{{date.fnm_sun}}` (first such weekday of next month), `{{date.weeks2}}`, `{{date.weeks3}}`, `{{date.weeks2_ago}}`, `{{date.weeks3_ago}}`. Do not rely on them outside extraction prompts.

**Fork on an extracted enum.** To route from one node to several paths, extract an enum and branch with `equals`. This is more reliable than several competing `matches_intent` transitions.

```json
{
  "name": "menu",
  "node_type": "conversation",
  "task_message": "Tell the caller the order status in one sentence. Then ask whether they want to change the delivery address, cancel the order, or end the call.",
  "extraction_schema": [
    {
      "name": "next_action",
      "type": "string",
      "enum_values": ["change_address", "cancel", "done"],
      "description": "What the caller chose. Empty if unclear.",
      "min_confidence": 0.7
    }
  ],
  "transitions": [
    { "target_node": "change_address", "description": "Change address", "condition": { "logic": "or", "conditions": [ { "variable": "next_action", "operator": "equals", "operand": "change_address" } ] } },
    { "target_node": "cancel_order", "description": "Cancel", "condition": { "logic": "or", "conditions": [ { "variable": "next_action", "operator": "equals", "operand": "cancel" } ] } },
    { "target_node": "goodbye", "description": "Done", "condition": { "logic": "or", "conditions": [ { "variable": "next_action", "operator": "equals", "operand": "done" } ] } },
    { "target_node": "menu", "description": "Unclear, stay", "condition": { "operator": "always" } }
  ]
}
```

Use extraction for user speech. For API responses use `response_mapping` (tools-and-code.md). It is deterministic and needs no model call.

## End-call nodes

An `end_call` node hangs up. It has a `terminal` object and no outgoing transitions.

```json
{
  "name": "goodbye",
  "node_type": "end_call",
  "on_enter": { "type": "silent" },
  "disable_inactivity_monitor": true,
  "transitions": [],
  "terminal": {
    "type": "function",
    "function": {
      "name": "closing_end",
      "handler": "__function__:end_call",
      "parameters": {
        "type": "object",
        "properties": {
          "message_mode": { "type": "string", "default": "custom" },
          "spoken_message": { "type": "string", "default": "Thank you for calling. Goodbye." }
        }
      }
    }
  }
}
```

| Parameter | Meaning |
|---|---|
| `message_mode` | `custom`: say `spoken_message`. `llm`: the model writes the farewell from `llm_prompt`. `none`: hang up without a farewell |
| `spoken_message` | The fixed farewell for `custom`. `{{var}}` works |
| `llm_prompt` | The instruction for `llm` |
| `interruptible` | `true` opens a short window after the farewell in which the user can still speak. Default: hang up as soon as the agent stops speaking |
| `trigger_timeout` | Length of that window in seconds |
| `trigger_pattern_both` | Farewell phrases, separated by `\|`, that do not cancel the close. Anything else the user says in the window cancels the close and returns the turn to the agent |

Rules:

- **The farewell comes from the terminal, not from `on_enter`.** A node with an `on_enter` line and `message_mode: "none"` hangs up silently. Put the sentence in `spoken_message` and set `on_enter` to `{"type": "silent"}`.
- Set `disable_inactivity_monitor` to `true` and `transitions` to `[]`.
- **The call's `endedReason` is the terminal's `function.name`.** The node name does not affect it. Pick a name that describes the outcome.
- Use several end-call nodes with different farewells and function names when outcomes differ.
- If you set `interruptible`, also set `trigger_pattern_both`. Without a phrase list every polite reply cancels the hang-up. The window is timed on a wall clock and a chat simulation cannot measure it.

Verified in a working builder: `message_mode: "none"` with a silent `on_enter` ends the call when the node is reached. The agent says its goodbye in the previous conversation node.

## Limits

| Limit | Default | Notes |
|---|---|---|
| `max_node_turns` | `10` | Cap on user turns in one node. Only user messages count. Tool results and agent messages do not. There is no "unlimited" value |
| `max_turn_transition` | none | Where to go when the cap is reached. Without it the engine records the overrun and continues with normal routing, so the cap changes nothing |
| `truncation_strategy` | `keep_all` | `keep_all`: full history. `keep_recent`: system message plus the last `truncation_window_size` messages. `summarize`: older messages are replaced by a model-written summary |
| `truncation_window_size` | `10` | Used by `keep_recent` and `summarize` |
| Extraction `min_confidence` | `0.95` | See "Extraction schema" |
| Code `timeout_ms` | `30000` | See tools-and-code.md |

Notes:

- Truncation applies to the dialogue model only. Extraction and routing run before it.
- Give every node that sets `max_node_turns` a `max_turn_transition`. The working builder sets `max_node_turns` to 60 and 80 on its conversation nodes without a `max_turn_transition`. Its calls ended well below those counts, so the behaviour at the cap is not confirmed by it.
- Size the cap from real conversations. A node that handles a whole call can need dozens of user turns.
- The maximum call length in a simulation is set with `maxCallDurationSeconds` (api.md).

## Design rules

- Use `snake_case` node keys that describe the step.
- Keep dialogue in `task_message`, routing in `transitions`, data capture in `extraction_schema`.
- Every path must reach an `end_call` node.
- Put deterministic conditions before `matches_intent` conditions.
- Every passthrough node ends with an `always` transition.
- A transition back to an earlier node is supported.
- Split a step into its own node when it has strict rules of its own or forms a clear state. Keep related optional actions together in one conversation node with several tools.

## Complete example

A clinic assistant. It collects a service and a day, looks up free slots, lets the model book one with a tool, and ends the call.

```json
{
  "initial_node": "collect",
  "system_prompt": "You are the phone assistant of a dental clinic. Speak English. Keep every turn to one or two short sentences.",
  "test_variables": { "patient_id": "p_test", "first_name": "Dana" },
  "global_nodes": {},
  "nodes": {
    "collect": {
      "name": "collect",
      "node_type": "conversation",
      "on_enter": { "type": "tts", "text": "Hello {{first_name}}, this is the clinic. Which treatment would you like to book, and on which day?" },
      "on_enter_first_entry_only": true,
      "task_message": "Find out which treatment the caller wants (checkup, cleaning or filling) and on which day. Ask one question at a time. Do not call a tool in this turn.",
      "extraction_schema": [
        { "name": "treatment", "type": "string", "enum_values": ["checkup", "cleaning", "filling"], "description": "Treatment the caller wants", "min_confidence": 0.7 },
        { "name": "wanted_day", "type": "date", "description": "Day the caller wants the appointment", "min_confidence": 0.7 }
      ],
      "max_node_turns": 12,
      "max_turn_transition": "goodbye_no_booking",
      "transitions": [
        {
          "target_node": "find_slots",
          "description": "Treatment and day are known",
          "condition": {
            "logic": "or",
            "conditions": [
              {
                "logic": "and",
                "conditions": [
                  { "variable": "treatment", "operator": "is_set" },
                  { "variable": "wanted_day", "operator": "is_set" }
                ]
              }
            ]
          }
        },
        { "target_node": "collect", "description": "Keep collecting", "condition": { "operator": "always" } }
      ]
    },
    "find_slots": {
      "name": "find_slots",
      "node_type": "api_request",
      "passthrough": true,
      "passthrough_default_transition": "offer",
      "on_enter": { "type": "silent" },
      "disable_inactivity_monitor": true,
      "pre_actions": [
        {
          "type": "function",
          "config": { "timeoutMs": 10000, "maxRetries": 2 },
          "function": {
            "name": "find_slots",
            "handler": "__function__:api_call",
            "description": "Get free slots for a day.",
            "parameters": {
              "type": "object",
              "properties": {
                "url": { "type": "string", "default": "https://api.example.com/v1/slots" },
                "method": { "type": "string", "default": "POST" },
                "headers": { "type": "object", "properties": { "Content-Type": { "type": "string", "default": "application/json" } } },
                "body": {
                  "type": "object",
                  "properties": {
                    "treatment": { "type": "string", "default": "{{treatment}}" },
                    "day": { "type": "string", "default": "{{wanted_day}}" }
                  }
                }
              }
            }
          }
        }
      ],
      "response_mapping": [
        { "path": "data.slots_text", "variable": "slots_text" }
      ],
      "transitions": [
        { "target_node": "goodbye_no_booking", "description": "The lookup failed", "condition": { "logic": "or", "conditions": [ { "variable": "find_slots_failure_count", "operator": "greater_than", "operand": 0 } ] } },
        { "target_node": "offer", "description": "always", "condition": { "operator": "always" } }
      ]
    },
    "offer": {
      "name": "offer",
      "node_type": "conversation",
      "task_message": "Free slots: {{slots_text}}\n\nOffer the earliest slot. If the caller refuses it, offer the next one. When the caller accepts a slot, read back the treatment, the day and the time and wait for a clear yes. Then CALL book_appointment. Saying that it is booked is not enough. After the tool result, tell the caller whether the booking worked and say goodbye.",
      "tools": [
        {
          "type": "function",
          "config": { "timeoutMs": 10000, "maxRetries": 0 },
          "function": {
            "name": "book_appointment",
            "handler": "__function__:api_call",
            "description": "Book one slot. CALL it only after the caller confirmed the read-back.",
            "parameters": {
              "type": "object",
              "properties": {
                "url": { "type": "string", "default": "https://api.example.com/v1/bookings" },
                "method": { "type": "string", "default": "POST" },
                "headers": { "type": "object", "properties": { "Content-Type": { "type": "string", "default": "application/json" } } },
                "body": {
                  "type": "object",
                  "properties": {
                    "patient_id": { "type": "string", "default": "{{patient_id}}" },
                    "treatment": { "type": "string", "default": "{{treatment}}" },
                    "slot_time": { "type": "string", "description": "Start time of the accepted slot, HH:MM, 24 hour", "default": "{{slot_time}}" }
                  },
                  "required": ["slot_time"]
                }
              }
            }
          },
          "response_mapping": [
            { "path": "data.booking_id", "variable": "booking_id" }
          ]
        }
      ],
      "max_node_turns": 20,
      "max_turn_transition": "goodbye_no_booking",
      "transitions": [
        { "target_node": "goodbye_booked", "description": "The booking was recorded", "condition": { "logic": "or", "conditions": [ { "variable": "booking_id", "operator": "is_set" } ] } },
        { "target_node": "goodbye_no_booking", "description": "The caller does not want any slot", "condition": { "operator": "matches_intent", "description": "The caller refused all offered slots or does not want to book" } }
      ]
    },
    "goodbye_booked": {
      "name": "goodbye_booked",
      "node_type": "end_call",
      "on_enter": { "type": "silent" },
      "disable_inactivity_monitor": true,
      "transitions": [],
      "terminal": {
        "type": "function",
        "function": {
          "name": "booked",
          "handler": "__function__:end_call",
          "parameters": { "type": "object", "properties": { "message_mode": { "type": "string", "default": "none" } } }
        }
      }
    },
    "goodbye_no_booking": {
      "name": "goodbye_no_booking",
      "node_type": "end_call",
      "on_enter": { "type": "silent" },
      "disable_inactivity_monitor": true,
      "transitions": [],
      "terminal": {
        "type": "function",
        "function": {
          "name": "no_booking",
          "handler": "__function__:end_call",
          "parameters": {
            "type": "object",
            "properties": {
              "message_mode": { "type": "string", "default": "custom" },
              "spoken_message": { "type": "string", "default": "No appointment was booked. You can call us again at any time. Goodbye." }
            }
          }
        }
      }
    }
  }
}
```

What the example shows:

| Node | Feature |
|---|---|
| `collect` | Fixed opening line, extraction with a `date` type, AND group, self-transition, turn cap with a target |
| `find_slots` | Passthrough `api_request` node, baked parameters, node-level `response_mapping`, failure counter, `always` fallback |
| `offer` | A tool the model calls, a model-filled body field, tool-level `response_mapping`, routing on the mapped variable |
| `goodbye_booked`, `goodbye_no_booking` | Two end-call nodes with different `endedReason` values |
